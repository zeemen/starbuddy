密级内部
〇结论

可以，但交出去的是"写代码"，不是"负责"

Claude Code 可以承担这个项目绝大部分的工程工作：四科盘点、契约与 Schema 起草、适配器、平台后端、前端壳、测试、评测框架、文档。按工程量估算，这是原计划里 70%–80% 的人天。

但有四类事不能、也不应该交给它：对学生负责的判断（判分是否公正、内容是否正确、话术是否合适——必须由教研签字）；对法律负责的判断（监管分类、监护人同意、数据出境——必须由人和律师定）；对真实世界的操作（生产部署、生产数据、支付、备案、招募试点家庭）；对方向的决定（七项待拍板、Gate 通过与否）。

一个直接的后果：瓶颈从"写代码的人手"移到"审核的人手"。Claude Code 一天可以开出十几个 PR，但一个面向未成年人的学习平台，每一个涉及家庭数据、计量、判分、人设的 PR 都需要人看。阶段 0 因此只能从 13 周压到约 10 周，而不是压到 3 周；寒假试点的日期锚点不变。

二最小团队

从 14 个角色到 6 个人

人投入职责
产品负责人 · Claude Code 操作者全职写 spec、驱动 Claude Code 会话、合并常规 PR、主持决策与 Gate
资深工程师（审查者）全职或 0.6审 [NEEDS-HUMAN] PR：迁移、RLS、计量、契约、第三方；维护 CLAUDE.md 与 hooks；兜底 Claude Code 卡住的问题
学科教研顾问 × 4各 0.3金标准标注、Rubric 分库、错因映射签字、人设话术签字、内容审核
合规顾问（外部）按需监管分类、隐私与同意、数据出境

原四科开发者如仍在，建议转为各自学科的"领域审查者"：确认盘点、审本科适配器 PR、回答 Claude Code 在 lessons.md 里留下的疑问。他们对各自代码的隐性知识，是 Claude Code 最缺的东西。

不建议的形态：没有资深工程师审查、由产品负责人一人合并全部 PR。这个项目处理未成年人的数据与付费，迁移、权限、计量上的一个疏漏，代价远高于省下的一个工程师。

三仓库 harness

让 Claude Code 在这个项目里"守规矩"的五件东西

Claude Code 的扩展层分工是：CLAUDE.md 提供常驻上下文，skills 提供按需加载的知识与工作流，MCP 连接外部服务，子代理提供隔离的上下文，hooks 负责自动化。官方建议 CLAUDE.md 控制在 200 行以内，参考资料放进按需加载的 skills（参见 code.claude.com/docs/en/features-overview）。配套启动包按此组织：

件内容为什么这样放
CLAUDE.md（根目录，50 行）仓库结构、10 条不可违反的规则、必停清单、工作方式、常用命令每个会话都会读到；规则写成可检查的句子，不写口号
hooks（settings.json + guard.py + post_edit.sh）PreToolUse：阻止推主干、强推、直接推迁移、读写密钥、生产操作、改教研金标准；PostToolUse：改动后跑 make check-fast，失败即回传安全红线不能靠"提醒"，要靠确定性拦截；已用样例验证可拦截
子代理 × 5inventory-auditor（只读盘点）、adapter-implementer（实现）、contract-guardian（契约守卫）、security-reviewer（安全审查）、persona-evaluator（人设回归）实现与审查分开上下文，审查者不背实现者的"思路包袱"；审查类子代理只给读权限
skills × 3/subject-inventory、/implement-adapter、/gate-check把每周重复的流程固化成一个命令
specs/_template目标、范围、可测试的验收标准、必停项自查、待人确认规格先于代码；没有已确认的 spec，skill 会停下

MCP 与外部连接

你已连接 GitHub、Supabase、Vercel。建议：GitHub 用于开 PR 与读 issue；Supabase 只连开发项目，并在 Supabase 侧为 Claude Code 使用的凭据设最小权限；Vercel 只用于预览部署。生产项目不配置给 Claude Code，生产部署由人在 CI 中手动批准。

并行方式

每个任务在独立 git worktree 与分支中进行，多个 Claude Code 会话可并行（例如同时实现阿鸦与知行的适配器）。并行度受人审能力约束：建议同时在途的 [NEEDS-HUMAN] PR 不超过 3 个，常规 PR 不超过 8 个。超过即暂停开新任务，先清审查队列。

六质量保障

为什么不能让 Claude Code 只给自己的代码写测试

同一个模型写实现又写测试，测试往往验证的是"代码做了它做的事"，而不是"代码做了该做的事"。对这个项目，最该防的恰好是后者：判分偏了、星星亮早了、家长看到了不该看的。三道独立防线：

  1. 教研金标准。判分一致率、人设期望答案、星亮门槛的验收样例由人标注，放在 evals/**/gold/，hook 阻止 Claude Code 修改。这是"该做什么"的唯一定义。
  2. 契约测试由契约生成。测试从 packages/contracts 自动生成，而不是由写适配器的同一个会话手写。
  3. 审查与实现分离。contract-guardian、security-reviewer、persona-evaluator 在独立上下文中只读审查；资深工程师审所有命中必停清单的改动。

另外两条纪律：Prompt 与人设的任何改动必须附回归前后对比；每两周由资深工程师随机抽 5 个已合并的常规 PR 复审，发现的问题写回 CLAUDE.md——同一个错误出现两次，就是 CLAUDE.md 该改了。

九成本与节奏

需要提前决定的三件事

  1. Claude Code 的使用方式与额度。并行会话数决定吞吐，也决定费用。建议阶段 0 以 2–4 个并行会话为上限，与人审能力匹配；订阅或 API 的选择以你所在组织的账户情况为准，价格与额度请以官方当前信息为准。
  2. Claude Code 本身的数据边界。开发环境里只有代码与合成数据，这是它可以工作的前提；这条也是合规顾问需要确认的供应商之一。
  3. 节奏。每天一次审查窗口（例如下午 4 点集中审 PR），每周五演示与复盘；复盘时把本周 Claude Code 的重复错误写进 CLAUDE.md，把重复的操作写成 skill。
