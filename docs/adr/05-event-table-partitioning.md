## 1. 背景

### 1.1 哪些是“事件表”
- `platform.evidence_event`：作答、OCR 转写、采分点证据、NPC 回合信号等原始证据（四份 adapter-design 都把现有数据落成 evidence_event）。
- `platform.attempt`：带归因的作答记录。
- 编排审计事件（ADR 03）。
- 计量流水 `usage_ledger`（一致性模型见 ADR 06，分区策略同样适用本 ADR）。

这些表只追加、几乎不更新，按时间增长，而且要长期保留作为“判断可追溯”的依据（完整方案第四章）。

### 1.2 规模预期
| 阶段 | 规模 | 来源 |
|---|---|---|
| 寒假试点 | 约 100 户 | 开发计划 |
| 春季内测 | 约 1,000 户 | 开发计划 |
| 2027 暑假 | 约 1 万注册 | 开发计划 |
| 规划上限 | 100 万注册、日活 15 万 | 技术实施蓝图 V2.0 第 7 节（待压测假设） |

按每个活跃学生每天产生约 200 条证据事件粗估（尚未实测）：内测期每天约 20 万行，1 万注册时每天百万行级别。**阶段 0 和阶段 1 的规模，单表加索引完全能扛。**

### 1.3 盘点发现
四科都没有可参考的事件表：文砺有 `assessment_event`，但 `ref` 是自由字符串，也不分区；其他三科没有事件表。没有历史数据要迁移。

---

## 2. 选项

### 选项 A：一开始就按月做声明式分区
- `PARTITION BY RANGE (occurred_at)`，每月一个分区，提前创建未来 3 个月的分区。
- 主键包含 `occurred_at`；幂等键的唯一约束也要包含分区键。

**优点**：以后不用做大表迁移；过期数据可以按分区归档或删除（配合 ADR 09 的保留期要求）。
**缺点**：唯一约束必须带分区键，幂等去重的设计要跟着调整；要有定时任务创建分区；境内托管能否使用分区管理扩展（如 pg_partman）取决于 ADR 10。

### 选项 B：先单表，到阈值再分区
**优点**：阶段 0 最简单。
**缺点**：以后要给在线的大表做分区迁移，风险高；证据事件是要长期保留的，迟早会到阈值。

### 选项 C：事件放进专门的时序或日志存储
**缺点**：跨存储的一致性和 RLS 都要重新做；阶段 0 规模不需要。**不推荐。**

---

## 3. 决定

**待签字。**

**建议采纳选项 A，但分区键和唯一约束先定下来，分区粒度留到压测后复核**：

1. `evidence_event`、`attempt`、审计事件、`usage_ledger` 从第一版迁移起就是按 `occurred_at` 的范围分区表，**暂定每月一个分区**。
2. **幂等键的唯一约束** = `UNIQUE (idempotency_key, occurred_at)`。Postgres 分区表的唯一约束必须包含分区键列，所以不能只对 `idempotency_key` 建唯一约束。为了让这个约束真正起到去重作用，写入方必须用**事件自身的发生时间**（而不是写入时间）作为 `occurred_at`，并且重试时原样带上，保持不变。计量账本需要不依赖时间的全局唯一性，见 ADR 06 第 2 条。
3. **必备索引**：`(student_id, occurred_at)`、`(subject, skill_node, occurred_at)`。
4. **分区维护**：定时任务提前建好未来 3 个月的分区；建分区失败要告警。实现方式（自写任务或 pg_partman）等 ADR 10 定了托管再选。
5. **保留期**：L2、L3 事件的保留期和删除方式按 ADR 09 与合规顾问意见定。分区让“按月删除”可行，但本 ADR 不定保留期。
6. **冲刺 5 压测后复核**：如果内测规模下单月分区过大或过小，调整粒度（按周或按季），只影响之后新建的分区。

---

## 4. 后果

### 正面
- 以后不用做在线的大表分区迁移。
- 保留期和删除可以按分区执行，满足“学习对话删除 / 导出”这类要求（完整方案第十一章）。

### 代价
- 唯一约束受分区键限制，幂等设计要多想一步（见上面第 2 条）。
- 跨分区查询（例如一个学生的全部历史）需要走索引，要在压测里覆盖。
