## 1. 背景
KGE 的编译层把原子（节点、采分点、题目标签、时政）编成面向学生与老师的知识页面（Markdown），由知识服务的 `page.get` 提供。页面是公共层内容，会被七科老师反复引用，错一处会在多次讲解里放大。
试点期（数学先行）有两个现实约束：
- 页面数量与变更频率都还不大，现在就建完整的页面库与审核台，投入与收益不匹配；
- 教研不写代码，但要能改页面、能看到每次改了什么、能挡住没过体检的改动。

KGE 第八章给的做法是：试点期页面放 Git 仓库，主分支保护，CI 跑程序体检，教研只经网页界面修改；规模上来后迁入 `kge.wiki_page`。

## 2. 选项
1. **直接进数据库（`kge.wiki_page`）并建审核台**：长期形态；但审核台 v0（4-G）还没建，试点期就要做编辑器、差异对比、版本回退，工作量大。
2. **Git 仓库 + 主分支保护 + CI 体检，教研经网页审核**（本 ADR 推荐）：
   - 差异、历史、回退、审核记录是 Git 托管平台自带的；
   - 体检用 CI 挡住，不靠人记得跑；
   - 规模上来后按触发条件迁入数据库。
3. **共享文档（在线文档）**：教研最熟悉；但没有程序体检、没有结构化差异，页面也难以被知识服务按版本读取。

## 3. 决定（待签字）
选项 2。
- **仓库**：
  - 单独的页面仓库，不放在本仓（CLAUDE.md 仓库结构）；托管在境内（ADR 09、10），具体平台见待人确认 #1；
  - 仓库只收公共层内容：作答、笔记、错因、学情档案页永远不进入（规则 13）；CI 加一道检查，拦截疑似个人信息与学生标识；
  - 群体数据只以聚合统计回流页面（如“常见错因”），并设最小人数门槛；门槛数值随 KGE 回流规则定，CI 检查引用的统计带人数且不低于门槛（规则 13）；
  - 个人信息误入时的紧急清除：CI 是第一道，不是唯一一道。发现误入后由技术负责人审批，按记录在案的流程改写历史清除（这是“不允许改写历史”的唯一例外），同时清理托管平台的缓存与复刻，并通知合规顾问；
- **主分支保护**：
  - 不允许直接推送，只能经合并请求；
  - 合并前必须 CI 通过、至少一名教研审核通过；高风险页面（类别见待人确认 #2）需两人；
  - 不允许强推与改写历史（个人信息紧急清除除外，见上）。
- **CI 程序体检**：
  - 结构检查：页面头部字段、引用的节点 ID 在已发布地图版本中存在（ID 正则与 `docs/design/kge/check_node_id.py` 一致）；
  - 内容检查：公式可解析，数学等式用 SymPy 验算（KGE-03）；禁语与人设中立检查（编纂规范 v1 人设中立）；
  - 体检不过不能合并。
- **教研的修改路径**：只经合并请求网页界面或最简审核台修改，不在本地直接提交；工程侧的批量改动（如编译器重建）同样走合并请求。
- **编译与发布**：编译器按每日合并窗口把主分支编进知识服务；页面带来源提交号，由知识服务把提交号映射到 `page.get` 已有的 `page_version`（与 `source_version`），不新增字段；若签字要求直接返回提交号，属契约变更，登记到 `specs/contract-conformance-sprint1/v1.0-review.md`。
- **迁入数据库的触发条件**（KGE 第八章）：多学科并行，或每周变更量超出合并请求的审核能力。迁移时保留提交历史与审核记录的对应关系；另起 ADR。

## 4. 后果
- 好处：
  - 试点期不用先建编辑器与版本系统，KGE-03 可以直接开工；
  - 每次修改都有差异、审核人与体检记录，满足“内容可追溯”；
  - 公共层与个人层在物理上分开（不同仓库），规则 13 更容易守住。
- 代价：
  - 教研要学会用合并请求网页界面；需要一份操作说明与一次培训；
  - 页面审核记录在 Git 平台，`kge.content_review` 里的审核记录要与提交号对应，两处要对账；
  - 以后迁入数据库有一次迁移成本。
- 需要同步的地方：KGE-03 spec（编译器、体检、合并窗口）、审核台 v0（4-G）spec、ADR 10 的托管清单。

## 5. 待人确认
1. 页面仓库托管在哪家境内平台（企业版代码托管服务、自建 GitLab 等），以及账号由谁开通：不写倾向，由技术负责人与合规顾问定。
2. “高风险页面”的类别与双人审核的范围：由教研负责人随编纂规范 v1 给出。
3. 每日合并窗口的时间与紧急修复通道。
4. 页面仓库的 CI 是否复用本仓的 `make` 目标（如节点 ID 检查），还是在页面仓库内单独维护。
