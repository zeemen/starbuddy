# ADR 03 · 编排用显式状态机，LangGraph 仅限复杂多步

## 1. 背景

### 1.1 总纲的设定
完整方案第六章：“显式有限状态流程（诊断 → 计划 → 教学 → 批改 → 复测），学科工具注册；复杂多步环节才引入 LangGraph。每一步幂等、超时、重试、审计；长任务持久化与断点恢复。”

### 1.2 盘点发现：四科都没有真正的编排
- **阿鸦**：“12 Agent”是 `lib/agents.ts` 里写死的数组，状态全是 `active`。`runLearningCycle` 是一个同步纯函数，按顺序调用规则函数、拼出 10 段文字，只有管理员页面调用。真正调模型的只有教练对话和拍照判分两个接口。第 ⑧ 步“验证 Agent”输出的是写死的宣传文案。
- **文砺**：`jobs` 表是空壳，长任务靠 `maxDuration=300` 撑着；LLM 超时 280 秒，但 Anthropic 路径没有超时。
- **知行**：LLM 超时 280 秒，路由 `maxDuration` 只有 60 秒，平台会先杀掉请求。
- **开口成章**：NPC 对话有一个确定性脚本引擎做降级，这是四科里唯一一个“失败时有明确下一状态”的设计。

结论：平台的编排要**从零建**，不存在要迁移的编排框架。

### 1.3 需要编排的流程
- 主流程：诊断 → 学习者模型更新 → 计划 → 教学 → 批改 → 错因归档 → 延迟复测（0 / 3 / 14 天）→ 回到模型更新。
- 长任务：试卷 OCR 诊断（p95 目标 < 90 秒）、英语异步批改、复测调度。
- 人工环节：`human_review_required` 为真时进入复核队列，等教研处理后再继续。

---

## 2. 选项

### 选项 A：显式状态机 + 持久化任务表
- 每个流程定义成有限状态机：状态、事件、转移、每个状态的超时和重试策略都写成代码或配置。
- 状态和每一步的输入输出落库（任务表 + 事件表），任何一步都可以重放和审计。
- 调度用队列和 Worker；复测用定时任务。

**优点**：行为可预测，可测试；天然支持幂等、断点恢复、审计；教研和家长可以看懂“学生现在在哪一步”。
**缺点**：灵活性低，新增一种流程要写代码。

### 选项 B：全部用 LangGraph
**优点**：图结构表达多步推理方便，社区生态好。
**缺点**：把判分、计量这些必须确定的步骤也放进 LLM 驱动的图里，难以证明“判分只来自验证器或 Rubric”（CLAUDE.md 第 3 条）；持久化和审计要额外配置；多一个依赖和版本漂移风险。

### 选项 C：沿用四科各自的请求内同步处理
没有持久化，无法支撑复测调度和人工复核环节。**不推荐。**

---

## 3. 决定

**待签字。**

**建议采纳选项 A，LangGraph 作为例外**：

1. **主流程和所有涉及判分、计量、写学习者模型的步骤，一律用显式状态机。** 状态机的定义放在 `services/learning`，每个状态写明：超时、最大重试次数、幂等键的构成、失败后的去向。
2. **LangGraph 只允许用在单个状态内部**，并且只限“生成类”的多步子任务（例如讲评课的讲解脚本生成）。它的输出必须回到状态机，由验证器或教研审核后才能进入下一步。引入前要按 CLAUDE.md 第 10 条检查许可证，并锁版本。
3. **人工复核是一个正式状态**：`awaiting_review`，带超时提醒（开发计划风险表：复核队列积压超过 72 小时要预警）。
4. **长任务异步化**：试卷诊断、英语批改返回 `202 + job_id`（与契约 spec 一致），不再靠拉长 `maxDuration`。
5. **每一步都写审计事件**，事件表的分区策略见 ADR 05。
6. **复测调度**（0 / 3 / 14 天）是状态机的定时事件，不是前端提醒。

## 4. 后果

### 正面
- 阿鸦 12 Agent 的“登记表”可以落成真实的状态和工具注册，覆盖状态以代码为准，不再以文案为准。
- 超时不一致的问题（知行 280 秒 vs 60 秒）在平台层统一解决。

### 代价
- 需要自建任务表、Worker、定时调度，阶段 0 冲刺 4 要留出工作量。
- 新流程需要写代码，不能只改 Prompt。
