## 1. 背景
- StarBuddy 的知识层原设计（KGE V1.1）自建全链路：知识地图骨架、原子层（题目打标、采分点、时政）、编译层页面、知识服务检索（页面优先、原子补充、向量兜底），以及证据与掌握。迁移 0011 等是草稿，从未在共享库执行；知识服务没有向量实现，全仓没有线上检索增强。
- 2026-11-01 用户决定：
  - 产品的标准知识与内容统一由 WeKnora（腾讯开源的知识库与 RAG 框架）运行，产品经 API 调用；
  - 专门的数据团队用“知识库供应链中台”（`zeemen/weknora-data-factory`，基于通用产品为 StarBuddy 定制）整理教材、教辅、试卷，覆盖初一到高三、各省、各出版社版本，试卷含答案；
  - 个人试卷、作答、成绩、判分不进 WeKnora。
- 盘点结论（inventory-report.md）：
  - 中台目前是通用产品，没有教育结构；
  - 交付给 WeKnora 时元数据没有发出；
  - 中台与 KGE 分别处在链路两端，几乎不重叠；
  - 需要先定三件事：真相源、检索方式、题目全文存放。

## 2. 选项
1. **WeKnora 取代 KGE**：知识地图、题目、评分细则、页面全部迁入 WeKnora，KGE 退役。
   - 问题：WeKnora 是检索与问答框架，没有稳定节点 ID、版本化地图、评分细则、掌握计算与教研签字闸门。规则 3（判分只来自验证器或评分细则）与星亮门槛都失去依托。
2. **WeKnora 只作 KGE 产物的检索投影**：标准内容仍以 KGE 为准，WeKnora 只是只读副本。
   - 问题：与用户决定不符。教材、试卷全文由中台加工后直接进 WeKnora，不经 `kge.*`；KGE 也不存题目全文。
3. **分工**（本 ADR 推荐，与 spec 默认值一致）：
   - WeKnora：**标准知识内容**（教材、教辅、试卷全文与解析）的运行与检索；
   - KGE：**知识地图骨架、评分细则、掌握计算与发布闸门**；
   - 中台：加工；
   - 两边用节点 ID 与题目 ID 关联。

## 3. 决定（待签字）
选项 3。

### 3.1 职责划分
| 组件 | 负责 | 不负责 |
|---|---|---|
| 知识库供应链中台 | 原始资料接入、解析、识别、切分、教育结构化（教材章节、知识点、题目拆分）、对齐 KGE 节点 ID、数据团队质检与教研签字（含签字记录）、交付到 WeKnora 生产库 | 不给节点命名或分配节点 ID；不处理任何个人数据；不发布进入判分与掌握的内容（标准答案、采分点、地图结构） |
| WeKnora | 标准知识内容（公共层）的存储、切块、向量、检索 | 判分、掌握、对学生的判断；个人数据 |
| KGE（`kge.*` + 审核台 + 知识服务） | 知识地图骨架（稳定节点 ID、关系、版本）、教材与地区投影、题目打标与元数据（不含全文）、采分点与评分细则、编译层页面（ADR 12）、教研签字与发布闸门、证据与掌握（个人层在 `platform.*`） | 不存题目全文与教材全文 |
| 个人层 `platform.*` | 作答、成绩、判分、错因、学情档案、个人上传 | 不进 WeKnora，也不进中台（规则 2、13） |

### 3.2 唯一调用入口
- StarBuddy 内部只有**知识服务**调用 WeKnora。学习服务、各科 Agent、点点、BFF 都经知识服务契约（规则 1）。
- 知识服务契约新增“标准知识检索”类工具，草案另起，属契约变更、必停。新工具沿用统一信封（`evidence_ids`、`confidence`、`source_version`、`model_version`、`human_review_required`）。`source_version` 带 WeKnora 知识库版本与内容 ID。
- 每次检索**必须**带结构化过滤维度：学科、学段年级、省份、出版社、版本、学期；适用时加考试年份、地区、考试类型。缺维度时拒绝，不做全库检索（沿用 KGE V1.1 的检索原则：先过滤，后检索）。

### 3.3 发布闸门：教研签字前置到中台（2026-11-01 用户决定）
- **讲解与检索用的标准内容**（教材、教辅、试卷全文与解析）：由数据团队在中台质检，其中教研人员签字。签字后直接交付到 WeKnora 的**生产知识库**，不再经 StarBuddy 审核台另签。知识服务只读生产库。
- 中台须保证签字可追溯、交付可撤回：
  - 每次交付记录签字人（教研角色）、签字时间、内容摘要、所交付的版本；
  - 只有教研角色可以批准交付；
  - 交付幂等，能按版本撤回或回滚。
  - 这些作为对中台的需求（spec 第三节）。
- **进入判分与掌握的内容**仍走 StarBuddy 审核台签字，不随中台直接上线：
  - 客观题标准答案进入验证器；
  - 主观题采分点进入 `kge.scoring_point`；
  - 知识地图的节点与关系变更；
  - 理由：判分与掌握计算是必停项（规则 3、CLAUDE.md 必停清单）。这一条是 Claude 按仓库规则保留的默认，**待用户确认**（见第 5 节）。
- 中台自己的拓扑设计里有“候选库 / 生产库”的分层，是否在中台内部保留由中台决定；StarBuddy 只认生产库。

### 3.4 题目与 ID
- 题目全文（题干、选项、答案、解析）只在 WeKnora。`kge.item_family` / `item_tag` 仍只存打标与元数据，与迁移 0011 的口径一致。
- 题目身份与准入仍在 `platform.item`，用其来源字段（迁移 0039 的 `source_ref`）记录 WeKnora 内容 ID 与中台内容 ID。
- **节点 ID 只由 KGE 分配**。中台按 StarBuddy 提供的节点表打标，低置信度进入人工确认，不自创节点。
- 判分仍只来自验证器或评分细则（规则 3）。WeKnora 里的答案与解析是讲解素材，不是判分依据。客观题标准答案进入验证器、主观题采分点进入 `kge.scoring_point`，两者都要经教研签字。

### 3.5 个人数据与查询
- 学生的提问文本作为检索查询经知识服务转发时，WeKnora 侧**不落库、不留日志**；做不到时，知识服务先去掉个人信息再转发，或者不转发原文。是否做得到，在 plan 阶段核实。
- 检索结果不回写知识库，只作为补页信号（KGE V1.1 原则）。
- 群体统计回流（例如常见错因）只以聚合形式，并满足最小人数门槛（规则 13）。

### 3.6 模型与出境
- **对话与增强模型：DeepSeek**（2026-11-01 用户决定）。中台的内容增强（类型、摘要、实体、关系）与 WeKnora 的对话、问答都用 DeepSeek。
- **保留切换**：模型经配置指定，不写死在代码里。中台与 WeKnora 都走 OpenAI 兼容接口，换供应商只改配置。新供应商须先在 `vendors.md` 登记并获批，再改配置。切换后要重跑中台抽取评测与知识服务检索评测（ADR 04 增补“模型升级附评测结果”的口径）。
- **接入平台待定**：可直连 DeepSeek 官方接口（需新登记供应商 `deepseek`），也可用火山方舟托管的 DeepSeek（`vendors.md` 已有 `ark` 条目，状态“待开通”）。
- **嵌入与重排另选**：DeepSeek 不提供嵌入与重排模型，WeKnora 向量检索所需的这两类模型需另定。可自部署开源模型（例如 BGE-M3 与 bge-reranker，KGE V1.1 原选型），也可用境内云厂商的嵌入服务。
- 以上模型都只用境内已备案模型。
- 统一登记到 `docs/compliance/vendors.md`，并按 ADR 04 的任务类型与数据级别路由。中台内部的模型调用不经 StarBuddy 路由，但供应商须在同一份登记表上获批。
- 沿用 2026-09-28 的决定：试点与生产不向境外发送任何数据。

### 3.7 范围与版权
- **学段**：中台加工初一到高三；StarBuddy 产品范围仍是初中。高中内容只作储备，不进入星图、诊断、掌握、今日计划（spec 决定记录第 7 条）。
- **版权**：按用户决定，进知识库的数据不考虑著作权与版权，不设授权准入；来源字段只用于过滤与追溯（spec 决定记录第 6 条）。这一项的判断与风险由用户承担。

## 4. 后果
- **契约**：知识服务新增标准知识检索工具（必停）。现有 10 个工具中，题目相关的 `item.search`、`item.similar` 是否改由 WeKnora 支撑，在契约草案里定。
- **KGE 检索原则调整**：原先“向量只兜底”改为“标准内容检索由 WeKnora 承担”。“先结构化过滤”和“页面优先”保留：编译层页面仍按 ADR 12 走 Git。页面是否也同步到 WeKnora，待定。
- **迁移**：
  - `platform.item` 来源字段要能记录外部内容 ID；
  - 判分与掌握相关内容经审核台签字时，可能新增对象类型（例如来自中台的标准答案）；
  - 这两项属迁移变更，必停，具体在 plan 阶段确定。
- **部署**：
  - 新增 WeKnora 及其依赖（向量库、对象存储、文档解析、模型服务）；
  - 中台本身（含 OCR 与语音转写）也要部署；
  - staging 的集群规格要重新评估（LT-03 决定记录第 18 条、待人确认第 20 条）。
- **对中台的需求单**：见 spec 第三节，将细化为可验收条目，提交到中台仓库。
- **风险**：
  - WeKnora 本体的能力（元数据过滤、按版本切换、查询日志、多知识库）尚未核实。本 ADR 的 3.2、3.3、3.5 都依赖这些能力，plan 阶段须先做技术验证。
  - 中台现有代码离教育场景要求差距大（报告第六节）。
