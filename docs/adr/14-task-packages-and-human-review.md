# ADR 14 · Claude Code 任务包格式与人审点

- 状态：**草稿，待签字**
- 日期：2026-09-28
- 决策人：待定（建议：技术负责人）
- 编号：开发计划 v2.0 写作 ADR 12；本仓库顺延为 14（`specs/plan-v2-alignment/spec.md` #2，已确认）
- 关联：
  - 开发计划 v2.0 第一章“任务包与人审点”、“人审不足时的精简方案”，“完成定义”；
  - CLAUDE.md“必须停下来请人确认的变更”“工作方式”；
  - 对照文档 `specs/plan-v2-alignment/spec.md` 第三节 #12；
  - `specs/_template/spec.md`；`.claude/agents/`（contract-guardian、security-reviewer、persona-evaluator 等）

> 本 ADR 不改迁移、契约、人设或计量，不属于必停项；但它定义必停项的清单本身，签字人应为技术负责人。

---

## 1. 背景
开发计划 v2.0 改为 Claude Code 主导开发：人写任务、审关键改动，Claude Code 写代码与测试。这要求两件事说清楚：
- **任务怎么下发**：v2.0 说“每个任务包写明目标、输入契约、验收测试、禁止修改的范围”；本仓库一直用 `specs/<任务>/` 目录（spec / plan / tasks / lessons），模板里有目标、范围、验收标准、必停项、依赖、待人确认，但没有单列“输入契约”和“禁止修改的范围”。
- **哪些改动必须人审**：v2.0 与 CLAUDE.md 各有一份清单，范围不完全相同（见第 3 节对照表）。

## 2. 选项
1. **沿用 `specs/<任务>/` 目录，模板补齐 v2.0 的四要素**（本 ADR 推荐）：已有 30 多个任务按这个结构写过，工具（`/spec`、各审查 agent）都认它；只需在模板里加“输入契约”“禁止修改的范围”两节。
2. **另建机器可读的任务包（如 YAML），由脚本下发**：便于统计与自动检查；但要写解析器与校验，人读起来不如 Markdown，与已有 spec 两套并存。
3. **只用议题系统（Issue）下发**：上手最快；但验收标准、待人确认、事后记录（lessons）分散在评论里，难以版本化，也不在仓库里。

## 3. 决定（待签字）
选项 1。
- **任务包 = `specs/<任务>/` 目录**：
  - `spec.md`：目标、范围（做 / 不做）、**输入契约**（依赖的契约、schema、ADR 的版本）、**禁止修改的范围**（目录或文件，与 CLAUDE.md 规则一致）、验收标准（可测试）、涉及的必停项、待人确认；
  - `plan.md` / `tasks.md`：可选，任务较大时写；
  - `lessons.md`：与 spec 的偏差、审查意见的处理、待人确认，完成时必写。
  - 目录名带任务包编号时沿用 v2.0：PLT-xx、KGE-xx、SIE-xx、ADP-科目-xx；已有目录不改名。
- **流程**：先起草 spec 并停下等人确认 → 实现 → 按改动类型跑审查 agent（contract-guardian、security-reviewer、persona-evaluator）并处理意见 → `make check` 与完成定义要求的专项测试 → 提交；合并前人审。
- **人审点**：以 CLAUDE.md“必须停下来请人确认的变更”为准（范围更宽，待人确认 #1 已按默认确定）；PR 描述首行写 `[NEEDS-HUMAN]`。对照如下：

| 人审点 | 开发计划 v2.0 | CLAUDE.md | 说明 |
|---|---|---|---|
| Schema 与迁移（数据迁移先在副本演练） | 有 | 有 | 一致 |
| 权限与 RLS 策略 | 有 | 有 | 一致 |
| 判分与掌握计算逻辑 | 有 | 有（列出证据权重、五道门槛与星亮门槛、复测调度、BKT 参数） | CLAUDE.md 更具体 |
| 判断模板与禁用词表 | 有 | 有，另加“画像可见范围” | CLAUDE.md 更宽 |
| 计量 | “计量扣次规则” | 计量与权益逻辑（含预留、结算、回滚、幂等与扣次规则） | CLAUDE.md 更宽 |
| Prompt 与人设语料 | 有 | 有，另加禁语表、转介话术 | CLAUDE.md 更宽 |
| 学科插件契约（`packages/contracts`） | 无 | 有 | 仅 CLAUDE.md |
| 教研标注的金标准数据 | 无 | 有（只能读） | 仅 CLAUDE.md |
| 新增第三方服务、模型供应商或数据出境路径 | 无 | 有 | 仅 CLAUDE.md |

- **人审不足时**：按开发计划 v2.0 的精简方案收缩范围（寒假封测只保留数学等），不降低人审点；人审点本身不因进度压力跳过。
- **完成定义**：`make check` 通过；涉及 Prompt 的跑人设回归；涉及计量的跑幂等测试；涉及知识的跑金标回归与体检；涉及画像的跑禁用推断与陈述—判断一致性测试；文档与 ADR 同步。失败不得声称完成。

## 4. 后果
- 好处：
  - 已有 spec 与工具不用迁移；新模板让“输入契约”“禁止修改的范围”成为必填，Claude Code 越界更容易在审查时发现；
  - 人审点只有一份权威清单（CLAUDE.md），不会两处各说各话。
- 代价：
  - 每个任务多写两节；
  - v2.0 文档与 CLAUDE.md 的清单不同，读 v2.0 的人需要知道以 CLAUDE.md 为准（本 ADR 的对照表即说明）。
- 需要同步的地方（签字后另开 PR）：
  - `specs/_template/spec.md` 加“输入契约”“禁止修改的范围”两节；
  - CLAUDE.md“工作方式”引用本 ADR；
  - `/spec` 命令按新模板起草。

## 5. 待人确认
1. 人审点以 CLAUDE.md 为准（已按默认确定，签字时复核）。
2. 已有 spec 是否补写“输入契约”“禁止修改的范围”：默认不补，只对新任务与改写中的冲刺 4 spec 生效。
3. 是否要求每个任务包附审查 agent 的原始输出：默认只在 lessons 里记处理结果。
4. 人审的签字方式（PR 审批即签字，还是另有记录表）：默认 PR 审批即签字，`[NEEDS-HUMAN]` 的 PR 至少一名对应领域负责人审批。
