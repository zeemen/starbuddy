## 1. 背景
平台对学生的每一句话都要能回答三个问题：凭什么这样认为、准不准、错了怎么改（SIE 第二章）。如果学科 Agent、点点、报告生成各自写结论，这三个问题都没法回答：
- 同一个学生会有互相矛盾的说法；
- 模型换版本后没法回放；
- 被推翻的结论可能还在别处展示。

SIE 把所有推断性认识统一存为“判断”，并规定写入与读取分离。本 ADR 把这条规定落到数据库层，让它不依赖代码自觉。

## 2. 选项
1. **只靠代码约定**：各服务约定不写判断。实现最省；但任何一个服务写错都没有兜底，Claude Code 实现偏离规格时也发现不了（SIE 风险表）。
2. **库层强制，单一写入角色**（本 ADR 选择）：
   - 新增数据库角色 `starbuddy_insight`，只有它能写判断账本；
   - 状态机、模板白名单、只追加的历史都由数据库触发器与约束强制；
   - 其他服务只能按 RLS 读。
3. **单独的判断数据库**：隔离最彻底，但与证据、掌握同库的事务一致性就没有了（ADR 02 共库分 schema 的理由同样适用）。

## 3. 决定（待签字）
选项 2。
- **位置**：判断账本放在新 schema `insight`（对照文档 #3：已有个人层表留在 `platform.*`，`insight.*` 只放新增对象）。
- **写入**：
  - 只有 `starbuddy_insight` 能写 `insight.claim`：没有 DELETE 权限，UPDATE 只开放值、置信度、证据、模型版本、状态、可见范围、到期时间几列；
  - 学科服务 `starbuddy_learning`、BFF `starbuddy_bff` 只能读；
  - 学科 Agent、点点、适配器只能经契约提交证据，由学习服务落库。
- **状态机**：
  - 假设 → 成立 → 待验证 → 成立 / 推翻；任何非终态 → 撤回；
  - 每次流转必须带原因（`insight.transition_reason`），原因必须与流转匹配；
  - 推翻与撤回是终态，终态判断的任何字段都不能再改；
  - 假设不能直接推翻，先转待验证（SIE-00 待人确认 #1，已按默认确认）。
- **历史**：
  - `insight.claim_history` 由属主为 `starbuddy_authz` 的触发器写入，洞察服务自己不能写，防止伪造；
  - 历史不能修改，只随判断在学生档案删除时级联删除。
- **模板白名单**：
  - 判断只能引用已审核的模板（`insight.claim_template`）；
  - 模板登记是人的操作（必停项），登记前过禁用推断词表检查（`docs/design/sie/sie_lexicon.py`）；
  - 没有模板的结论写不进账本。这就把“你不擅长数学”这类句子挡在账本层（CLAUDE.md 规则 12）。
- **可见性**：
  - 学生本人只看可见范围含 student 的非终态判断，有效绑定家长只看含 guardian 的，学科服务只看含 agent 的；
  - 推翻与撤回的判断任何前端都看不到；
  - 可见范围不能超出模板允许的上限。
- **推断必须有据**：`source_type = inferred` 的判断必须带证据 ID 与模型版本；每条判断必须有到期时间（会过期）。
- **过渡**：
  - 判断账本上线前，已合并的展示（星图、v0.9 契约的 report）按原样运行（CLAUDE.md 规则 11 过渡条款）；
  - 洞察服务的代码放在哪里（`services/learning` 内的独立模块，还是新服务），另行决定，不在本 ADR。

## 4. 后果
- 好处：
  - “可见陈述 100% 引用判断”“禁用推断 0”“删除覆盖全表”（Gate 0 画像底线）有库层兜底，不靠代码自觉；
  - 流转历史可用于离线回放与审计。
- 代价：
  - 洞察服务每次流转都要在同一事务里设置原因；
  - 模板变更要走人工审核，初期会拖慢首批模板上线；
  - 部署时登录角色不能同时继承 insight 与其他应用角色（0010 断言）。
- 需要同步的地方：攻击面清单、渗透测试范围（`docs/security/pentest/scope.md`）、权限快照（`db/tests/expected/`）都已随 0010 更新。
