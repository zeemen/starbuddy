# 讲评课教研验收清单（借鉴 OpenMAIC 的 ZPD 习题课验收） · 规格草稿

- 状态：**已确认（2026-11-26，用户“按建议，默认值都同意，开始实现”）**：第五节五条都按默认；清单条目仍待教研负责人签字。实现记录与差异见 lessons.md。
- 来源：OpenMAIC 借鉴分析 v1.1 第八节第 5 条（用户 2026-11-25“已合并，按建议起草 ZPD 验收清单的规格”）。
- **借鉴对象**：OpenMAIC 的 `eval/zone-of-proximal-development/README.md`（主干，2026-11-25 只读核查）。核查到的事实：
  - 它是一份**由测试者手动执行的检查清单**，分六节：
    - 名称与加载；
    - 帮完后把任务还给学生；
    - “已经会”与“还要支撑”；
    - 跨轮露答案；
    - 真实练习闭环；
    - 整节测验课与理论边界。
  - 测试输入都由测试者构造（“不是学生学习数据”）。每项报告实际结果，**不按关键词计分**，也没有数值门槛，不用模型判分。失败要写清按钮、输入、动作与结果。
  - 作答分三类记录：独立、受助、新任务。示范之后的重做只能检验功能，不能当首次独立表现；同一轮前面出现过的答案，不能算学生自己给出的证据；一次回答不能得出稳定的能力分。
  - 另有 `LOCAL_VALIDATION.md` 记了技能版本、模型与跑测基线。
  - 我们只借清单的结构与这几条判断原则，不引入它的代码或依赖。
- **依据**：
  - 证据情境 `evidence_kind`（独立 / 提示 / 迁移 / 延迟复测，迁移 0017；`services/learning/learning/mastery/evidence.py`）与 KGE 的五道门槛、星亮门槛；
  - 插件契约 `teach`（提示等级上限 `allowed_hint_level`，讲解不写关于学生的判断）；
  - `specs/stage-dsl-v0.2`、`specs/quote-verbatim-guard`、`specs/stage-point-to-ask`；
  - CLAUDE.md 规则 3、7、8、11、12、14。
- **必停项判断**：
  - 本任务只做清单的格式、记录格式与完整性检查，不涉及必停项；
  - 清单的条目内容属教研口径：这里只起草默认条目，教研负责人签字后才能用于验收，签字后改条目归教研；
  - 不改判分与掌握计算，不改契约、人设与金标数据，不接触留出集（规则 14）。

## 一、现状（2026-11-25 核对）
- **讲评课还没有**：开发计划 v2.0 把数学白板讲评课排在阶段 1 的 2 月。仓库里只有讲解白板（DSL v0.2）、样张页、阿鸦 `teach` v0；`teach` v0 是确定性的，只给提示阶梯与知识页面直出。
- **现有评测都是自动的**：`evals/`（人设、道法判分、知识编译、标注、影子评审、声纹盲测）要么跑脚本，要么对金标。没有一份**人工验收清单**的格式，没有统一的记录写法，也没有“填完了没有”的检查。
- **思路已经一致的地方**：我们的证据情境把作答分成独立、提示、迁移、延迟复测，比 OpenMAIC 的三类多一个延迟复测；掌握计算本来就不让看过高级提示的作答推门槛（`evidence.py`）。
  缺的是在讲评课上线前，由人逐项核对“产品实际记下来的情境对不对”“讲解有没有露答案”“帮完有没有把任务还给学生”。

## 二、默认做法
1. **清单文件** `evals/lesson-acceptance/checklist.yaml`：
   - 每条的字段：`id`（如 `A3`）、`section`、`must`（必过项还是观察项）、`setup`、`steps`、`expect`、`evidence_kind_expect`（这一条期望系统记下的证据情境，没有就留空）、`refs`。
     - `setup`：测试者要构造什么合成输入；
     - `steps`：怎么操作；
     - `expect`：应当观察到什么；
     - `refs`：依据的规则或规格。
   - 清单带版本号与签字栏（`signed_by`、`signed_at`）。没签字的清单只能做试跑，不能作验收结论。
   - 默认条目分六节，每节先起草 3–5 条，定稿归教研：

     | 节 | 核对什么 | 借鉴自 OpenMAIC |
     |---|---|---|
     | A 证据情境 | 首次独立作答记 `independent`；看过提示的作答记 `hinted` 并带提示等级；**看过示范或解答后的重做记 `hinted`，不记独立**；同一轮前面讲过答案的题，后面再答不记 `independent`；新题复核与讲过的题不同题目族才记 `transfer`；一次作答不点亮星 | 三类记录分开；示范后重做只检验功能；跨轮露答案 |
     | B 支架 | 学生卡住时补必要讲解后把一道题还给学生，等学生做；做对后减少帮助，给不露答案的新题；说“会了”的学生得到适度新挑战，不重复整段导入；前置不会的学生得到更窄的先备任务，不是更强的提示 | 帮完还给学生；“已经会”与“还要支撑” |
     | C 提交前不露答案 | 首题与新题在提交前都不出现答案；提示等级不超过平台给的上限；“再讲一遍”只重放讲解，不给答案 | 提交前不露答案；可选提示仍留学生一个动作 |
     | D 讲解内容 | 白板说、画、指对齐（DSL 与台词稿校验通过）；**预设的错例不能说成是这个学生的错**，引用学生原话必须逐字（`quote-verbatim-guard`）；讲解里没有关于学生的判断；禁用推断词表不命中 | 预设错例不当学生的错 |
     | E 路线与记录 | 求助路线、跳过路线都走一遍；中途退出再进、刷新后记录还在；家长端只看到判断渲染句（规则 11） | 求助、跳过两条路都走；刷新后记录还在 |
     | F 边界 | 只问概念的请求不生成讲评课；超出学习范畴的话走转介；人设一致性另跑 `make eval-persona`，清单只核对“跑过、通过” | 理论边界 |

2. **记录文件**：每次验收一份，存放位置见第五节第 4 条。
   - 记录头：
     - 清单版本；
     - 被验收的各版本：DSL、适配器、人设 Prompt、模型路由、契约；
     - 环境：只限 staging 或本地，不连生产（规则 9）；
     - 测试者与日期；
     - 声明“测试输入均为测试者构造的合成数据”。
   - 每条记录写：
     - **实际结果**（文字）；
     - 结论（`pass` / `fail` / `blocked` / `n_a`）；
     - 系统实际记下的证据情境（有 `evidence_kind_expect` 的条目必填）；
     - 失败或受阻时的复现：按钮、输入、动作、结果；
     - 截图或日志的引用（只写相对路径或编号，不嵌原图）。
   - **不按关键词计分，不用模型判**：结论由测试者按 `expect` 逐条给出。
3. **完整性检查** `evals/lesson-acceptance/check.py`（纯标准库加 PyYAML），新 make 目标 `lesson-acceptance-check`，并入 `make check`：
   - **校验清单本身**：
     - 字段齐全；
     - id 唯一；
     - `evidence_kind_expect` 只能取四种情境；
     - `refs` 指向的文件存在；
     - 签字栏的格式。
   - **校验记录**：
     - 覆盖清单里的每一条，不多不少；
     - 每条结论合法；`fail` / `blocked` 必须有复现；
     - 有 `evidence_kind_expect` 的条目，必须记了实际情境；实际与期望不同时，结论不能是 `pass`；
     - 必过项为 `n_a` 时必须写理由；
     - 记录头齐全，并有合成数据声明。
   - **防真实数据**：拒收形似手机号、身份证号、真实学校全名的文字。手机号与身份证号的形状规则参照仓库已有的写法（如 `services/bff/src/observability/log.ts` 的脱敏规则），实现时核对后引用同一口径；学校名按配置词表。
   - **验收结论按规则算出**：必过项全部 `pass` → 通过；任何必过项 `fail` 或 `blocked` → 不通过；清单未签字 → 只算“试跑”。
     结论由程序按这条规则得出，不由测试者手填，避免填错。
   - 仓库里只放一份合成的示例记录（`examples/sample-record.yaml`，明显占位），用来测检查器；真实验收记录不进本仓库（第五节第 4 条）。
4. **与自动检查的分工**：清单只管人看才能判断的事。能自动的，比如 DSL 校验、引语校验、禁用推断、人设回归，清单里只写“跑过、通过”并引用结果，不重复做。
   A 节的证据情境，讲评课上线后可以从 staging 合成账号的证据记录自动比对。那一步另起，不在本期。
5. **测试**：
   - 检查器单测：每条规则的正例与反例；示例记录通过；
   - 反例覆盖：缺条目、多条目、`fail` 没写复现、证据情境不一致却记 `pass`、必过项 `blocked` 却得出通过、未签字清单得出“通过”、记录里出现形似手机号的文字；
   - 变异：几条关键规则改坏后测试能发现；
   - `make check-fast` 通过；零新依赖（PyYAML 已在学习服务的依赖里，实现时核对检查器用哪个环境跑）。

## 三、不做
- 讲评课本身、它的内容生成、发布闸门与审核台（阶段 1 · 2 月）。
- 自动比对证据情境（讲评课上线后另起）；验收记录的线上填写页面。
- 改证据情境的定义、权重、五道门槛与星亮门槛（判分与掌握计算，必停）。
- 把清单当成模型评测的金标，或拿它去调参。

## 四、验收
- 清单文件、记录格式、检查器与示例记录齐备。
- 检查器能挡住第二节第 3 条列的各类问题，示例记录通过。
- `make lesson-acceptance-check` 并入 `make check`，在 CI 里跑。
- 清单默认条目覆盖 A–F 六节，每条都写清 `setup`、`steps`、`expect` 与依据，并注明“待教研负责人签字”。

## 五、待人确认（括号里是默认）
1. **清单归谁**：工程起草默认条目，教研负责人逐条修改并签字，签字后改条目归教研（默认）；还是由教研从零写，工程只做格式与检查器？
2. **通过规则**：必过项全部 `pass` 才通过，`blocked` 也算不通过，观察项不影响结论（默认）；还是允许必过项有 1 条 `blocked` 时有条件通过？
3. **哪些条目是必过项**：A 节（证据情境）、C 节（提交前不露答案）、D 节里“预设错例不说成学生的错”与“没有关于学生的判断”是必过项，其余是观察项（默认）；请教研调整。
4. **真实验收记录放哪**：不进代码仓库，放教研的验收台账；仓库只放合成示例与检查器（默认）。也可以放进仓库，但只许测试者构造的合成输入，同样由检查器把关。
5. **验收频率**：讲评课首次上线前全清单跑一遍；之后每次改人设 Prompt、提示阶梯或讲解生成，跑 A–D 节（默认）。也可以每次发布都跑全清单。
