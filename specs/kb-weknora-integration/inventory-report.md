## 一、结论摘要

1. **两边目前几乎不重叠，正好在链路两端。**
   - 中台做的是"原始资料 → 加工 → 交付"，包括多格式解析、OCR、语音转写、切分、人工确认、导入 WeKnora。这一段 StarBuddy 只有离线导入工具，没有通用资料加工能力。
   - StarBuddy 的 KGE 做的是"知识地图 + 原子 + 编译页 + 证据与掌握"。这一段中台和 WeKnora 都没有。
2. **中台现在是通用产品，不是教育产品。**
   - 学科、年级、教材版本只是批次级的一个 JSON 属性。
   - 没有章节、知识点、题目结构、答案、解析、采分点、难度。
   - 题目只是一整段文本。
   - 评测里教育样本的主题、实体、关系得分都是 0%。
   - PRD 里写的教育维度（教材版本、知识点、题目—解析—错因绑定、不得跨版本误用）都是【规划】。
3. **交付给 WeKnora 的内容会丢掉结构。**
   - 适配器只发 `title` 和 `content`：每个文件合成一篇 Markdown。
   - 学科、年级、版本等元数据在代码里组装好了，**但没有发出去**（`batches.py:600-607`、`weknora.py:71-76`）。
   - 单元类型、摘要、实体、关系也都不交付。
   - 因此"按教材范围过滤检索"在现有代码下做不到。
4. **和 KGE 的核心设计有几处根本性张力**，需要先定原则再谈接入：
   - 谁是知识的真相源：KGE 骨架和原子，还是 WeKnora 知识库。
   - 检索方式：KGE 是"页面优先、原子补充、向量只兜底、先结构化过滤"；WeKnora 是向量 RAG。
   - 题目全文：KGE 规定题干、答案、解析不进 `kge.*`；中台和 WeKnora 存的是全文。
5. **合规上有几处硬缺口，都碰到必停项。**
   - 中台会把原文**不经脱敏**发给 OpenAI 兼容的大模型。
   - 没有用量记录和预算控制。
   - 没有个人信息检测；原件明文存放，也无法删除。
   - StarBuddy 的 `vendors.md` 里还没有任何已批准的模型供应商，并且决定了"试点与生产不向境外发送任何数据"。
   - WeKnora 本身需要嵌入、重排、对话模型，这些都算新增模型供应商。
6. **中台工程成熟度是早期原型**：没有迁移工具（Alembic），没有 PostgreSQL 驱动，镜像里不含 OCR 和语音转写，交付不幂等，重新处理会抹掉人工确认结果，评测集是合成语料。

## 二、两边各是什么

| | 知识库供应链中台（weknora-data-factory） | StarBuddy 知识层（KGE + 知识服务 + 审核台） |
|---|---|---|
| 定位 | WeKnora 的上游加工台：原始资料 → 结构化、可追溯的知识数据 → 导入 WeKnora（README:3） | 全产品的知识骨架与内容成长引擎；知识节点（星）是诊断和掌握的主单元（KGE V1.1:358） |
| 服务对象 | 行业、产业、企业知识；用途有三类模板：教育辅导、文旅导览、通用（`catalog.py`） | 南京初中七科；三种学科型：结构型、能力阶梯型、观点定位型 |
| 技术栈 | FastAPI + SQLAlchemy + SQLite；React 19 + Vite；进程内任务队列 | Python FastAPI 知识服务、学习服务；PostgreSQL（`kge.*` 是草稿）；TS BFF |
| 规模 | 后端约 8.7k 行，前端约 5.5k 行，114 个测试 | 知识服务、学习服务、审核台、tools/kge-*，迁移 0011–0043 等 |
| 成熟度 | 第一个可运行的纵向切片，默认用演示模式交付 | 代码已实现；**kge 相关迁移只在一次性测试库跑过，没有在任何共享库执行**；只有合成数据 |
| 在线检索 / 问答 | 不做，交给 WeKnora | 知识服务提供 7 个公共工具（HTTP + MCP），用 jieba + BM25；**没有向量**；全仓没有线上 RAG 用法 |

## 三、能力逐项对照

| 能力 | 中台 | StarBuddy | 对照 |
|---|---|---|---|
| 资料接入 | 【实现】上传 PDF、Office、文本、图片、音视频；周期数据源，按指纹做增量（`sources.py`） | tools/kge-* 离线导入 legacy 题库与种子，只读输入，只生成 SQL 文件 | **中台补位** |
| 解析 / OCR / 语音转写 | 【实现】pypdf、python-docx 等；PaddleOCR；faster-whisper。只出纯文本，**不支持公式、表格、版面**（README 限制 2） | KGE 规划里选型 MinerU / PaddleOCR【规划】 | 中台补位；但数学、理化的公式和表格是硬缺口 |
| 切分 | 【实现】按标题、中文序号、篇名规则切，约 900 字一块 | 编译器 `build_chunks` 对公共层页面切块 | 两边各切各的，对象不同 |
| 知识结构 | 【实现】只有"知识单元"，类型对教育只有 `knowledge_point` 和 `question` | 【草稿】`kge.knowledge_node`：稳定 ID（学科.领域.主题.节点.细目）、7 种节点类型、认知层次、地图版本 | **中台没有骨架**，也不能为节点命名或分配 ID |
| 关系 | 【实现】同批次内关系，大模型类型中教育相关的只有 prerequisite、contrast、extension；规则关系只对文旅生效 | 【草稿】`kge.knowledge_edge` 7 种类型，配合 `validate_map_version` 检查环、孤点、悬空引用 | 中台关系只在批次内、没有校验；不能直接当地图边 |
| 教材 / 地区投影 | 批次级属性：省份、年级、学科、出版社、版本、学期 | 【草稿】`kge.textbook_projection`：版次、册、章、页码、原句与哈希，需核对；`region_projection` | 粒度差很大：批次级对比节点级 |
| 题目 | 整段文本，题干和答案不拆分 | 【草稿】`kge.item_family` / `item_tag` 只存打标与元数据，**题干、答案、解析不进库**；题目身份与准入在 `platform.item`；有版权状态 | 存放原则冲突，见第五节 |
| 评分细则 | 没有 | 【草稿】`kge.scoring_point`，只增不改，按 rubric 版本；规则 3 要求判分只来自验证器或评分细则 | 中台没有；判分链路不能依赖它 |
| 人工审核 | 【实现】确认或忽略问题、采纳或驳回关系；**不能编辑单元**；重新处理会删光人工结论 | 【实现，依赖草稿表】审核台：差异与风险分级、两人签字、发布与撤下、页面对账 | KGE 的发布闸门远比中台严；中台确认不等于教研签字 |
| 版本与发布 | 交付一次就是一次导入，可以撤销；**不幂等**，可以重复交付 | 地图"主.次.修订"版本，一科只有一个已发布版本，有 ID 迁移表，有发布记录 | 中台没有版本概念 |
| 检索 | 不做；WeKnora 负责（向量 RAG） | 页面优先 → 原子补充 → 向量兜底；**先过学科、版次、年级、地区、地图版本、权限的结构化过滤**；查询结果不回写成页 | **检索哲学不同**，见第五节 |
| 大模型 | 【实现】OpenAI 兼容接口，可选；原文前 1200 字直接发送；用量不落库 | 统一经学习服务模型路由（按任务和数据级别）；只登记了两家，**都没批准**；测试用假供应商 | 需要统一到 StarBuddy 的路由与登记制度 |
| 租户与权限 | 【实现】工作区与四种角色，在每个路由里手写过滤；子表没有 workspace_id；WeKnora 凭证全局共用一套 | 数据库角色加行级安全（`starbuddy_kge` 唯一写入方，`kge_read` 只能看到已发布内容） | 隔离强度不同 |
| 评测 | 11 份合成语料，属自评 | 金标准由教研标注并只读；留出集封存，构建方不接触（规则 14） | 中台评测不能作为教育质量的依据 |

## 四、数据对应关系（只列能否对应，不设计映射）

| 中台对象 | StarBuddy 最接近的对象 | 能否直接对应 |
|---|---|---|
| `batches.attributes` 里的 province、grade、subject、publisher、edition、semester | `platform.curriculum_version`（region、grade、textbook_version、subject…）与 `kge.map_version` | 部分。中台是自由 JSON，缺地图版本、考试年份 |

## 五、与 StarBuddy 设计、规则的冲突点

1. **真相源（规则 2 的精神，以及 KGE"原子为准，页面为用"）**
   KGE 规定节点 ID、边、投影、评分细则在 `kge.*`，页面在 Git 仓库（ADR 12），两者冲突时以原子为准。如果 WeKnora 成为"整个产品的知识底座"，就要定下：它存的是 **KGE 产物的投影**（只读副本，供检索），还是**新的真相源**。后者意味着 KGE 骨架和发布闸门要重做，并且 0011 等迁移草稿受影响。
2. **题目全文存放**
   `kge.item_tag` 注释写明题干、答案、解析不进库（0011:276）。中台和 WeKnora 都存全文。试卷和教辅还有版权问题（`license_state`）。
3. **检索方式**
   KGE V1.1:479-481 规定先做结构化过滤，向量只兜底。目前 WeKnora 拿不到过滤维度，因为元数据没发出去，"不得跨教材版本误用"就无从保证。
4. **公共层与个人层（规则 13）**
   中台只处理公共资料，方向一致。但仍需明确：WeKnora 里**不得**进入作答、错因、学情档案；"查询结果不回写成页"如何在 WeKnora 侧保证；群体数据回流须满足最小人数门槛。
5. **模型与出境（必停项）**
   中台的增强模型、WeKnora 的嵌入、重排、对话模型都算新增模型供应商。"试点与生产不向境外发送任何数据"已经定了（plan-v2-alignment 8.1 #10），嵌入请求的数据级别还没认定（decisions-2026-10-09:120）。中台目前以 DeepSeek 为示例，原文不脱敏直接发送。
6. **判分来源（规则 3）**
   判分只能来自验证器或评分细则。WeKnora 的问答结果不能进入判分；评分细则的真相源仍须是 `kge.scoring_point` 或它的替代物。
7. **留出集与金标（规则 14）**
   中台的评测语料与 StarBuddy 金标、留出集要隔离：留出集不得流入中台或 WeKnora。
8. **许可证（规则 10）**
   中台仓库本身没有许可证声明。PaddleOCR、faster-whisper 等的许可证要按 StarBuddy 惯例逐一核实；WeKnora 的许可证也需核实。

## 六、中台自身的缺口（按对接影响排序，均有代码依据）

1. **元数据没有交付**：`batches.py:600-607` 组装了，`weknora.py:71-76` 没发。
2. **没有教育结构**：章节、知识点、题目拆分、答案、解析、错因、评分细则都没有；题目与知识点没有关联（`catalog.py:86-124`，`classification.py:208-233`）。
3. **人工结论不持久**：重新处理会删掉单元、问题和关系（`processing.py:699-701`）；不能编辑单元；单元的 status 永远停在 `auto_checked`。
4. **交付不幂等**：已交付的批次可以再次交付（`batches.py:563`）；部分失败没有续传；真实 WeKnora 调用没有任何测试。
5. **公式、表格、版面不支持**：对数学、物理、化学试卷是硬缺口。
6. **大模型治理缺失**：原文不脱敏外发（`enrichment.py:230-231`）；用量丢弃（`llm.py:144`）；没有预算和限流；重新处理会重复调用。
7. **合规缺失**：没有个人信息检测；原件明文存放且不能删除；没有版权和授权字段；数据源没有路径白名单，也没有 SSRF 防护（`services/sources.py:140-204`）；有默认管理员和演示口令；没有登录限流和 CSRF 防护。
8. **租户隔离偏弱**：子表没有 workspace_id，全靠路由里的手写校验；企业主体是写死的 3 个演示值；WeKnora 凭证全局共用。
9. **工程化**：没有 Alembic，没有 PostgreSQL 驱动，没有 CI；镜像不含 OCR 和语音转写；任务租约只在启动时回收；Web 镜像构建不锁依赖。

## 七、StarBuddy 侧必然受影响的范围（事实清单）

- **契约（必停）**：`knowledge-service.v0.9.yaml` 的 10 个工具与统一信封；插件 API 里的 `knowledge_page`、`scoring_points`、`node_path`、`item_family`；`source_version` 中地图段的写法。
- **表与角色（必停）**：`kge.*` 全部，以及 `platform.item`、`curriculum_version`、`skill_node`、`content_signoff`、`release_record`、`mastery_estimate` 节点键、`evidence_event.map_version_id`；角色 `starbuddy_kge`、`starbuddy_kge_read` 及其行级安全。
- **直接读 kge 表的代码**：学习服务的 `plan.py`、`mastery/*`、`practice/store.py`；BFF 的星图 v1、`shell-routes`；洞察服务的读授权。
- **内容管线与发布**：tools/kge-*，审核台的签字、发布、对账，页面快照格式，ADR 12 的 Git 页面仓库。
- **部署**：知识服务部署已暂缓（LT-03 待人确认第 20 条）；staging 集群暂缓（决定记录第 18 条）；WeKnora 及其依赖的资源需求还没评估。

## 八、需要你拍板的问题（起草规格和 ADR 之前）

1. **WeKnora 的角色**：KGE 产物的**检索投影**（只读副本，真相源仍是 `kge.*` + 页面仓库），还是**新的知识真相源**（KGE 骨架与发布闸门要改造）？
2. **中台的角色**：只做**原始资料加工、候选生产**（产出进入 KGE 的候选队列，由审核台签字后发布），还是直接把内容**发布到线上**（导入 WeKnora 即生效）？
3. **题目与试卷**：全文放哪里（WeKnora / 中台 / `platform.item` 侧另存），以及版权状态由谁核对？
4. **模型**：中台增强、WeKnora 嵌入、重排、对话分别用哪家境内供应商？是否允许原文发送（数据级别）？这需要走供应商登记流程。
5. **优先级**：先补中台的教育结构（知识点、题目拆分、元数据交付），还是先定 StarBuddy 侧的接入边界？
6. **两个仓库的关系**：中台仍是独立产品（同时服务文旅等其他行业），还是为 StarBuddy 定制分支？这决定了教育结构加在哪一层。

确认上述问题后，按仓库流程在本目录起草 `spec.md` 与 ADR 草稿（必停项另行标注 `[NEEDS-HUMAN]`）。
