## 一、边界（中台必须守住的四条线）

中台方面不需要实现什么，但必须遵守。下面每条需求都不得突破这四条。

1. **不处理任何个人数据**。学生的试卷、作答、成绩、判分、错因不进中台，也不进 WeKnora（ADR 16 第 3.1、3.5 节）。中台只收公共资料。
2. **不分配知识节点 ID**。节点 ID 只由 StarBuddy 的 KGE 分配。中台按 StarBuddy 提供的节点表打标，不新建节点（ADR 16 第 3.4 节）。
3. **不发布判分内容**。下面三类内容不随中台直接上线，要导出给 StarBuddy 审核台签字（ADR 16 第 3.3 节）：
   - 客观题标准答案（进验证器）；
   - 主观题采分点（进 `kge.scoring_point`）；
   - 知识地图结构的变更建议。
4. **生产库只收教研签字后的内容**。StarBuddy 只读 WeKnora 生产库；测试库与生产库分开（ADR 16 第 3.3、3.4b 节）。

### ZT-01 教育结构模型（P0）
**现状**
- 学科、年级、省份、出版社、版本、学期都只是批次级的自由 JSON（`catalog.py:86-124`）。
- 知识单元的类型对教育只有 `knowledge_point` 和 `question`（`classification.py:208-233`）。
- 题目是一整段文本，题干和答案不分开。

**要做**
1. 资料层级：学段（初中 / 高中）、学科、年级、省份、出版社、版本（含版次年份）、学期、册次、章、节、单元。层级要落到**每个单元**上，不只落在批次上。一个批次可以含多章。
2. 题目拆分：题干、选项、答案、解析分成独立字段，另加题型、难度、分值。试卷题目还要带：试卷名、考试类型（中考、高考、期中、期末、其他）、年份、地区，以及在卷中的题号。
3. 题目与知识点关联：一道题可以关联多个知识点（关联目标是 ZT-02 的节点 ID）。
4. 复合题（材料题、大题含小问）：保留父子结构，小问可以单独引用。
5. 高中内容照常加工和交付，用学段字段区分（决定记录第 7 条）。

**验收**
- 上传一份带答案的初中数学期末试卷和一章教材，处理后：
  - 每道题的题干、选项、答案、解析分别可见、可单独编辑，题号与原卷一致；
  - 每个教材单元都带完整的层级字段；
  - 缺必填层级字段的单元进入待确认，不能交付。
- 抽检 50 道题，题干与答案拆分正确率不低于 95%（以教研人工核对为准）；不达标的题进入待确认，不能静默交付。

### ZT-02 按 StarBuddy 节点表打标（P0）
**要做**
1. 导入 StarBuddy 提供的**节点表**（格式见附录 A.2），按地图版本存放；同一学科可以有多个地图版本，打标时指定用哪一版。
2. 知识点单元、题目打上节点 ID，每条标签带置信度与依据（命中的原文片段）。
3. 低于阈值的标签进入人工确认；人工可以改标、删标、加标。
4. **不得新建节点**。遇到节点表里没有的知识点，记为“缺节点”问题，汇总后导出给 StarBuddy；由 KGE 决定是否新增节点。
5. 地图版本升级时，按 StarBuddy 提供的 ID 迁移表批量改标，改不了的进入人工确认。

**验收**
- 节点表里不存在的 ID 无法写入标签（接口与界面都拒绝）。
- 导出的“缺节点”清单包含：原文片段、所在资料与位置、建议的父节点。
- 换地图版本后，所有标签都指向新版本里存在的节点，或者处在待确认状态。

**StarBuddy 侧依赖**：节点表导出。KGE 的地图表还是迁移草稿，没有在任何共享库执行过。联调前，StarBuddy 先给一份按附录 A.2 格式的种子节点表（合成或种子数据），正式节点表随地图发布提供。

### ZT-03 交付带元数据与稳定 ID（P0）
**现状**
- 元数据在 `api/batches.py` 的交付流程里组装了，适配器只发了 `title`、`content`、`status`、`channel`（`integrations/weknora.py:71-76`）。
- 每个文件合成一篇 Markdown，单元的类型、层级、标签都不交付。

**要做**
1. 按附录 A.1 的字段，把元数据随文档交付给 WeKnora。具体用 WeKnora 的哪种机制（文档标签、元数据字段，或者按维度分库），等 StarBuddy 的 WeKnora 技术验证得出结论后定。中台的适配层要能按验证结论配置。
2. 交付粒度：一道题、一个教材小节分别是一个可检索单位，不再把整份文件合成一篇。复合题按 ZT-01 第 4 条保留父子关系。
3. 每个交付单位有**中台内容 ID**：重新处理、重新交付都不变（内容变了版本号加一，ID 不变）。
4. 题目的题干、答案、解析在交付内容里分区标注，便于 StarBuddy 的知识服务决定返回哪些部分（ADR 16 第 3.4a 节；契约草案里定）。

**验收**
- 在测试库里，用“学科 + 年级 + 省份 + 出版社 + 版本 + 学期”的组合检索，只返回该组合的内容；换一个出版社版本，结果不重叠。
- 同一份资料处理两次、交付两次，中台内容 ID 集合不变。
- 有一个对真实 WeKnora（测试库）的自动化测试，覆盖“带元数据交付后能按元数据过滤取回”。

### ZT-04 交付幂等、续传、按版本回滚（P0）
**现状**
- 交付只拦 `processing` 和 `delivering` 状态，已交付的批次可以再交付一次，WeKnora 里出现两份（`api/batches.py:581`）。
- 交付中途失败，直接返回失败，已导入的部分不续传（`integrations/weknora.py:78-85`）。
- 已有整次撤销（`/deliveries/{id}/revoke`）。

**要做**
1. 按中台内容 ID 做更新或替换：同 ID、同版本重复交付不产生新文档；版本变了就替换旧文档。
2. 部分失败可以续传，只补没成功的那部分。
3. 每次交付是一个**交付版本**，可以整体回滚到上一个交付版本。
4. 内容被后续版本取代后，WeKnora 里的旧文档要同步删除或下线（中台已不再交付 `superseded` 片段，但已在 WeKnora 里的旧文档还在）。

**验收**
- 同一批次连续交付两次，WeKnora 里的文档数不变。
- 模拟交付到一半失败，续传后文档数等于应交付数，没有重复。
- 回滚后，WeKnora 里的内容与上一个交付版本一致（按内容 ID 与版本号比对）。

### ZT-05 教研角色与签字记录（P0）
**现状**：四种角色是管理员、编辑、审核、只读，审核角色就能导入知识库（`permissions.py`）；交付只记发起人。

**要做**
1. 新增**教研**角色。只有教研能批准交付到生产库；管理员也不能代签。
2. 每次交付到生产库前必须有签字记录：签字人（教研账号）、签字时间、本次内容摘要（新增、修改、下线各多少，涉及哪些学科年级）、所交付的交付版本号。
3. 签字记录不可修改、不可删除，可以导出。
4. 同一份内容的加工人和签字人不能是同一账号。
5. 交付到测试库不需要签字（ZT-06）。

**验收**
- 非教研角色调用“交付到生产库”接口，返回无权限。
- 没有签字记录的交付版本无法发到生产库。
- 加工人本人签字被拒绝。
- 签字记录导出与 WeKnora 生产库内容可以按交付版本一一对上。

### ZT-06 测试库与生产库分开（P0）
**现状**：WeKnora 的地址、凭证、目标库是全局配置一套（`config.py`），所有工作区共用。

**要做**
1. 每个工作区（产品线）分别配置**测试库**与**生产库**两个目标；凭证按工作区存放。
2. 交付时明确选目标。界面上生产库要醒目区分，交付前二次确认。
3. 中台不得写入 StarBuddy 编译页所在的知识库或命名空间。编译页由 StarBuddy 自己同步（ADR 16 第 3.4a 节）。

**验收**
- 测试库的交付不影响生产库，反之亦然（各交付一次后分别核对文档数）。
- 中台配置里找不到对编译页所在库的写入目标，接口也拒绝写入。

### ZT-07 判分类内容单独导出（P0）
**要做**
1. 客观题标准答案、主观题采分点候选，按题目导出成**判分候选包**（格式见附录 A.3）。这个包交给 StarBuddy 审核台，不交付到 WeKnora 生产库的判分用途。
2. 判分候选包与 WeKnora 里的讲解内容用同一个中台内容 ID 关联。
3. 地图结构的变更建议（ZT-02 的缺节点、关系建议）也走这个导出口。

**说明**：WeKnora 里的答案与解析可以作为讲解素材照常交付；判分只认审核台签字后的验证器与采分点（规则 3）。

**验收**
- 导出包里每道题都带：中台内容 ID、内容版本、节点 ID、答案或采分点、来源，以及中台侧的教研签字记录编号。
- 导出包里没有任何个人数据（ZT-09 的检测对导出包同样生效）。

### ZT-08 交付清单查询接口（P0）
**用途**：StarBuddy 要按交付结果同步自己的题目身份表（`platform.item` 的来源字段记 WeKnora 内容 ID 与中台内容 ID，ADR 16 第 3.4 节）和打标表（`kge.item_tag`）。

**要做**
1. 提供只读接口（或定期导出文件），按交付版本列出每个交付单位：中台内容 ID、内容版本、WeKnora 文档 ID、目标库（测试或生产）、附录 A.1 的元数据、状态（有效、已取代、已下线）、签字记录编号。
2. 支持增量查询：给出上次同步的交付版本，只返回之后的变化。
3. 接口用单独的只读凭证，只能看本工作区。

**验收**
- StarBuddy 用增量查询同步两次，第二次只拿到新增与变化的部分。
- 被回滚或下线的内容在清单里状态正确。

### ZT-09 个人信息拦截（P0）
**背景**：期中、期末试卷的扫描件可能带学生姓名、学号、班级、手写作答与分数。规则 2、13 要求这类内容不进中台和 WeKnora。

**要做**
1. 上传和识别后检测个人信息：姓名栏、学号、班级、手机号、身份证号、手写作答痕迹、批改分数。
2. 检出的资料标记为“含个人信息”，不能交付，只能由数据团队重新上传已清理的版本。
3. 含个人信息的原件、识别缓存（包括云端 OCR 的缓存）要能彻底删除，并留删除记录。

**验收**
- 用合成的“带姓名栏和分数的试卷”样本（不得用真实学生试卷，规则 8），检出后无法交付。
- 删除后，原件、识别结果、缓存文件都找不到；删除记录可以查。

### ZT-10 模型与第三方服务治理（P0）
**现状**
- 大模型、视觉模型、云端 OCR 都走可配置的地址。已有 LOCAL_ONLY 硬闸：开启后不调用公网地址（`services/egress.py`）。
- 大模型返回的用量会解析，但没有落库（`integrations/llm.py:160`）。
- 内容增强把原文前 1200 字发给模型（`services/enrichment.py:29`）。
- 没有预算与限流；重新处理会重复调用模型。

**要做**
1. **主机白名单**：只允许调用 StarBuddy `docs/compliance/vendors.md` 里已批准供应商的主机，配置成别的地址时拒绝启动该能力，并如实标注“未获批”。目前涉及：
   - 对话与增强：DeepSeek 官方接口（`deepseek`，待开通 / 待登记）；
   - 视觉模型：阿里云百炼的通义视觉模型（`bailian`，待开通 / 待登记）；
   - 云端 OCR：百度智能云文档解析（`baidu-ocr`，待开通 / 待登记）。
   - 上述供应商在合规负责人批准前都是“未获批”；在此之前联调用本地引擎，或者用 LOCAL_ONLY。
2. **用量落库**：每次调用记录供应商、模型、调用目的、输入输出 token 数或页数、批次、时间；按工作区、按月汇总。
3. **预算与限流**：按工作区设月度上限，接近上限告警，超过时停止调用、如实标注。
4. **不重复调用**：内容没变的段落不再调模型（数据源增量已经做到，见 ZT-12；同一批次重新处理也要做到）。
5. **只发公共资料**：发给模型的只能是公共资料。ZT-09 检出含个人信息的资料，一律不发。
6. **可切换**：模型经配置指定，换供应商只改配置（决定记录第 9 条）。

**验收**
- 把大模型地址配置成白名单外的主机，增强能力显示“未获批”，没有任何出网请求（用抓包或模拟传输层验证）。
- 处理一个批次后，用量表里有逐次记录，汇总数与模型返回的用量一致。
- 预算设为很低的值，超过后调用停止，批次标注原因。

### ZT-11 公式、表格、版面（P1）
**现状**
- 已接百度“文档解析（Unlimited-OCR 2）”：能还原 LaTeX 公式与 Markdown 表格。代价是正文由云端模型重排，不再逐字等同原图，并且数据出内网。
- 默认是 `local_first`：本地 PaddleOCR 先识别，效果不足的页再送云端。
- 本地引擎不支持公式与表格。

**要做**
1. 数学、物理、化学资料的公式以 LaTeX、表格以结构化形式保留到**交付正文**，不在交付时被拍平成纯文本。
2. 云端重排过的正文要标记来源（哪一页、用的哪个引擎），并且必须经人工抽检后才能交付。
3. 几何图、受力图、实验装置图等插图：原图随题目保留引用；视觉模型生成的描述只作附注，不混进正文（中台现有原则，保持）。
4. 云端 OCR 用百度智能云文档解析（2026-11-02 用户决定），只有在 `baidu-ocr` 登记获批后才能在 StarBuddy 工作区开启（ZT-10 第 1 条）。默认的 `local_first`（本地先识别、不足的页才送云端）保持。

**验收**
- 用 20 道含公式和表格的合成或公开样题，交付到测试库后，公式能被 LaTeX 渲染器正确渲染，表格行列与原题一致；正确率由教研抽检确认。

### ZT-12 人工结论持久化、单元可编辑（P1）
**现状**
- 数据源的段落级增量（`services/paragraphs.py`）已经做到：未变段落直接复用旧单元，ID 稳定，确认状态保留；被取代的标记 `superseded`，不删。
- 但**同一批次重新处理**时，仍会先删光该批次的关系、问题和单元（`services/processing.py:829-831`），人工结论全部丢失。
- 不能编辑单元；新单元状态一律是 `auto_checked`（`services/processing.py:608`）。

**要做**
1. 同一批次重新处理也按段落指纹复用，已人工确认的单元、标签、关系不被覆盖。
2. 单元可编辑：正文、类型、层级字段、题目拆分、节点标签，都可以由人改；改动留痕（谁、何时、改前改后）。
3. 单元有明确的人工状态：待确认、已确认、已驳回；只有已确认的单元能进入签字（ZT-05）。

**验收**
- 确认 10 个单元并改其中 3 个后重新处理同一批次，这 10 个单元的内容、状态、标签不变。
- 任一单元能查到完整的编辑历史。

### ZT-13 来源字段（P1）
**要做**：每份资料与每个交付单位带来源：资料名、出版社或命题单位、版本或版次、年份、地区、页码或题号。用于检索过滤与追溯。按决定记录第 6 条，**不设授权准入**，不需要授权状态字段。

**验收**：交付清单（ZT-08）里每个单位都有来源字段，缺失的不能交付。

### ZT-14 工程化（P1）
**现状**：默认 SQLite，依赖里没有 PostgreSQL 驱动；自写的补列脚本（`migrations.py`），没有迁移工具；没有 CI；真实 WeKnora 调用没有测试；镜像已可通过 `EXTRAS` 构建参数装入 OCR 与语音转写。

**要做**
1. 支持 PostgreSQL，并引入迁移工具（例如 Alembic）；迁移可以回退。
2. 加 CI：lint、类型检查、单测、对 WeKnora 测试库的契约测试。
3. 部署形态按 ADR 16 第 3.4b 节（2026-11-02 用户确认云上部署）：
   - 中台的服务与数据库放在与 StarBuddy 同一阿里云账号、北京地域、同一 VPC，只开内网；
   - OCR、视觉模型可以在数据团队本机跑，只把识别结果交给云上的中台；
   - 交付到 WeKnora 只能由云上的中台服务发起，本机不直连 WeKnora；
   - 本机访问云上中台走专线或 VPN（StarBuddy 侧随集群恢复一起规划）。
4. 备份与恢复脚本（已有 `scripts/backup.py`、`restore.py`）纳入定期演练。

**验收**：CI 在每次提交上运行并通过；迁移在一份 PostgreSQL 副本上能升级、回退、再升级。

### ZT-15 安全加固（P1）
**现状**
- 默认管理员口令写在配置默认值里（`config.py:150`），演示登录默认开启（`config.py:147`）。中台的 `.env.example` 已提示交付前修改。
- 没有 CSRF 防护与登录限流。
- 远程清单数据源没有地址白名单与 SSRF 防护；目录数据源没有路径白名单（`services/sources.py`）。

**要做**
1. 生产配置下：默认口令或演示登录未关闭时拒绝启动。
2. 加 CSRF 防护与登录失败限流。
3. 数据源：目录只能在配置的根目录下；远程清单只能访问白名单主机，拒绝内网与元数据地址。
4. WeKnora 凭证按工作区加密存放（与 ZT-06 一起做），日志不打印凭证。

**验收**：带默认口令以生产配置启动时失败；远程清单指向内网地址或云元数据地址时被拒绝。

### ZT-16 许可证（P1）
**要做**：仓库补 LICENSE；列出依赖许可证清单（PaddleOCR、PaddlePaddle、faster-whisper、pypdfium2 等），StarBuddy 按规则 10 复核后才部署。

**验收**：清单覆盖 `pyproject.toml` 与前端 `package.json` 的全部直接依赖，并标出许可证类型。

### ZT-17 教育质量评测（P2）
**要做**
1. 中台自建教育评测集：由数据团队教研标注，覆盖题目拆分、层级字段、节点打标、公式表格。
2. 指标进 CI，模型或规则变更前后附对比。
3. **不得使用 StarBuddy 的金标准与留出集**；StarBuddy 也不会提供（规则 14）。

**验收**：评测报告包含各学科的拆分正确率、打标准确率与召回率。

- 每行：`node_id`、`map_version`、`subject`、`name`、`aliases`、`parent_node_id`、`node_type`、教材投影（出版社、版本、册、章、页码，可以有多条）。

- 格式：JSON Lines。交付渠道在联调时定，不经 WeKnora。
