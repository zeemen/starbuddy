## 第一部分：盲测方案与评测框架（已实现，待评审）

### 实现要点
- **方案**：`plan.md`——候选准入门槛与评分项、两阶段测试集及各自前提、指标口径、角色分离与随机编号、合规清单 C1–C12、执行手册（执行人、机器、步骤、报告提交位置）。
- **框架** `evals/voice-blind/`：只用标准库 + PyYAML（测试加 pytest），不引入新依赖。
  - 供应商接口 `AsrVendor` / `PronunciationVendor` 只有抽象类；测试断言 `vendor.py` 里没有具体实现、仓库里只有 `fake-*` 合成假供应商。
  - 请求只含随机条目编号、音频引用与元数据、语言；**ASR 请求不含参考文本**，任何请求都不含口音、噪声标签与样本编号（测试断言）。
  - 音频只是引用：清单里 `synthetic://`（程序生成的静音或合成波形元数据）或 `store://`（执行环境里的存储键）；拒绝 http(s)、file://、绝对路径、`..`；
    合成清单只能用 `synthetic://`、真实清单只能用 `store://`；框架不读音频字节，测试断言目录里没有音频文件。
  - 报告只含汇总、分组指标、样本编号与标签；不含音频引用、参考文本、转写原文、供应商名（只用 VA / VB / VC）、时间与本机路径；同样输入逐字节相同；
    拒绝写进任何 `gold/`（大小写不敏感，报告与 `--results` 都查）。
  - 非合成清单的结果文件（含转写原文）放在仓库里会被拒绝。
  - 合成样例 `reports/sample-synthetic/`：三家假供应商（准确 / 对口音样本系统性出错 / 随机出错），报告头标“流程样例，不是评测结论”，测试核对它是最新的。
  - 无网络：测试把 `socket.connect` / `create_connection` / `getaddrinfo` 换成断言失败后跑完整 sample + score；静态扫描源码不得导入网络库、subprocess，不得读环境变量或出现密钥字样。
- **测试**：73 条（编辑距离与 CER / WER 手算含中英混排、空参考、全错、规范化开关；分位数；Pearson / Spearman 含并列；音素一致性含漏判与多判；
  自助法可复现与分位位置手算；清单校验；报告确定性与不含原文；盲测；gold 拒绝；无网络）。
- **变异**：`scripts/mutations.py` 27 条（编辑距离、空参考、合计口径、规范化开关、分位数、秩、召回 / 精确、音素对齐、自助法种子与分位、请求泄露参考文本、
  提交顺序、编号、清单协议与个人信息扫描、报告泄露原文、样例标注、gold、真实结果位置），全部被发现。
- **Makefile**：末尾追加 `voice-blind-eval-test`（测试 + 变异，约 40 秒），并加进 `check` 的依赖列表（只改了这一行的末尾）。
  系统 python 缺 pytest 时非严格跳过、严格失败；可传 `PYTHON=services/learning/.venv/bin/python`。

### 与 spec / 任务说明的偏差（都是口径选择，写进了 plan 第 3 节与报告的“配置”）
1. **中英混排的 CER**：缺省拉丁字母、数字逐字符计（“AI”= 2 个单位），与“按字”一致；`--zh-latin-as-word` 可改为连续拉丁串按一个单位计（接近常见的混合错误率 MER）。
2. **音素对齐**用最长公共子序列（`align` 的替换代价 3 > 删除 + 插入），让相同标签尽量对上；普通 Levenshtein 在并列时会把相同标签错开，低估一致性。
3. **缺结果**按转写为空（全部删除）计入错误率，另报条数；发音评测缺结果按专家音素都“没判”计。
4. **分位数**用最近秩法（不插值），与仓库既有自助法（`evals/persona/scorer/compare_report.py`）同一写法；样本少时 p95 就是最大值附近。
5. **区间**是单家单指标的百分位自助法；没有做两家之间的配对差值区间（见待人确认 4）。
6. **成本**不由框架计算：报价表在 plan 第 5 节由采购填写。
7. 另写了 `evals/voice-blind/README.md`（仿 `evals/kge-compile/README.md`：文件表、清单格式、命令），方案正文在 plan.md。
8. Makefile 目标写成**单个 shell 块**：跳过分支 `exit 0` 后不再执行后面的命令。观察到 `kge-compile-eval-test` 等既有目标的“跳过”行后面还有独立的命令行，
   缺依赖时非严格模式可能仍会失败——本任务不改它们，只记录。

## 第二部分：语音分钟计量辅助（2026-10-05）
spec 设计要点 3：平台侧计量辅助（按预计分钟预留、按实际时长结算、失败回滚、幂等键，`voice_realtime` 按分钟向上取整、`voice` 池），用合成调用证明预留 / 结算 / 回滚与幂等（库上测试）。不改任何计量函数与额度（必停项），PR 首行 `[NEEDS-HUMAN]`。spec 待人确认 #4（只计 `voice_realtime`、宵禁与单日上限同样生效）按默认。

### 做了什么
- `services/bff/src/voice/minutes.ts`：内部模块，没有路由、没有调用方、不接任何供应商、不处理语音数据。资源固定 `voice_realtime`、来源方法固定 `teach`（契约 TeachRequest 写明“实时语音另计 voice_realtime”）；必带小写 UUIDv4 幂等键，`usage_id` 由它派生并与库返回值核对。
- 预留直接调 `platform.meter_reserve`（`meter.ts` 的 `reserve()` 类型只认 grade / diagnose，用它就要改计量模块），结算与释放复用 `settle` / `release`；H6 计量入口登记表 `METER_CALLERS` 已登记，参数用静态断言锁成常量。
- 口径：时长先校验为有限非负数并取整成整数毫秒，再 `ceil(ms / 60000)`；超出预留按预留封顶结算并报出；预计分钟封顶到 29（有效期 30 分钟减 1 分钟结算余量），封顶时报 `estimate_capped`；会话最长时长取 min(预留分钟, 到期前 60 秒)。
- 状态：确定失败整笔释放；会话或结算抛异常、时长非法、会话报未知，一律按“结果未知”处理（不释放、不结算、报 `session_result_unknown`，返回 `unknown` 带原因），交给过期任务回收；同 key 找回仍在预留中的那笔返回 `in_progress`、不开会话；结算是幂等重放时返回 `completed_previously`、不报已扣。
- 宵禁、单日上限、留存态全部由 `meter_reserve` 判定，BFF 不另算。
- 测试：单测（取整、入参校验在连库前、错误信息固定文案、usage_id 不一致不开会话、不导入网络 / 文件 / 音频、不挂路由）；库上集成测试（取整边界、预留 / 结算 / 回滚 / 过期、同 key 并发只开一次会话、结果未知后重试不开会话、21:50 预留 21:55 重试不跨进宵禁、单日上限、留存态、家长不能代预留、异常与非法时长）；变异“语音：”15 条。

### 测试
`make bff-test` 通过；`BFFMUT_FILTER=语音` 15/15；`make check-fast` 通过。全量 bff-mutation 留给严格检查（之前一次两轮运行写同一日志，结果不算数）。

### 审查意见处理（按用户“按默认建议处理审查意见”）
- 阻断（安全）：同 key 找回仍在预留中的那笔时会再开一段完整会话，并发或重试少扣，并能绕过单日上限与宵禁（旧预留跳过宵禁检查）。已改为返回 `in_progress` 不开会话，补三条集成测试与变异。
- 其余：异常按结果未知处理；幂等重放不报已扣；预留句柄只留服务端（注释写明，接路由前补 H6 用例）；错误信息固定文案；补“不核对 usage_id”“no_time_left 不释放”变异；时长规整；预计分钟封顶 29。
- 不改计量模块：`reserve()` 放宽类型属于改计量模块（必停），保留两处 `meter_reserve` 调用点，靠 `METER_CALLERS` 登记与静态断言防口径分叉；以后 `reserve()` 加校验或指标时须同步语音。

### 经验
- 同 key 找回的预留不能再开会话：旧预留不再过宵禁检查，有效期加时长会把会话开进宵禁，并发重试还会开出多次会话。
- 计量相关异常一律按“结果未知”处理，交给过期任务回收；结算幂等重放必须报未扣费。
- 封顶后“结算余量”只在有时钟偏差时起作用，变异测试要用注入的时钟偏差覆盖。
- 全量 bff-test 共用一个库，额度配置会被别的测试改，库上断言不写死发放量；同一时刻的预留行序不定，断言前先排序。
- 停后台 make 任务后要确认子进程真的停了再开新一轮，否则两轮写同一个日志。
- “页面：整页不设总时限”这条变异在满载时会漏检，单独重跑能发现。

### 待人确认
1. 单笔上限与预留有效期都是 30 分钟，实际最多扣 29 分钟；预计超过 29 时不再被库拒绝而是按 29 预留——是否调有效期或单笔上限（额度配置，必停），封顶本身是否算计量规则变化。
2. 会话中途失败整笔不扣；是否按已用时长扣。
3. 语音与 ai_active_time 共用同一个单日上限（0015 按所有分钟类资源合计），是否符合预期。
4. 来源方法用 teach（库也允许 grade）；账本里这笔的 `source_idempotency_key` 是语音会话键，不对应任何插件 teach 调用，以后对账要单独处理语音。
5. 结果未知返回 `unknown` 而不是抛出，接路由时映射成“暂不可用”；同 key 遇 `in_progress` 时前端等待还是换新 key（换新 key 旧预留占额度最长 30 分钟）。
6. 失败路径上的释放本身抛异常时照常抛给调用方，预留留给过期任务回收。
7. `/tmp/starbuddy-bffmut.*` 下有 3 个早先变异测试留下的临时目录，由人决定是否删除。
