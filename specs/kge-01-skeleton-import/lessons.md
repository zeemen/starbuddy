# KGE-01 骨架导入 · 经验与待人确认

## 交付
- 导入器 `tools/kge-inventory/src/import/`（`build.ts` 纯函数、`extract-topic.ts` 隔离子进程加载 legacy、`main.ts` 命令行）；`make kge-import` 生成种子。
- 种子 `db/seeds/kge/aya-fun-0.1.0/`：`import.sql`（以 `starbuddy_kge` 身份单事务写入）、`worklist.md`（103 条工作项）、`import-report.json`。
- 测试：映射规则单测 8 组（随 `kge-inventory-test`）；`make kge-import-test` 在一次性库上执行种子、跑发布前校验、用合成补齐文件验证可发布，已接入 `make check`。

## 结果（按默认映射）
- 45 个节点导入 24 个（知识点 10、能力型知识点 10、方法 4）；不导入 21 个：能力子节点 C 7 个、没有错因大类的 P 14 个。
- 本专题内能连的前置边 9 条，没有环、没有传递边；两端都在本专题、但有一端未导入而没连的边 26 条（报告 `unconnected_edges`）。
- 发布前校验：`orphan` 14、`missing_boundary` 20，与工作单逐条一致；不能发布。
- 合成补齐（P 按知识点、边界填占位、孤点挂一条合成前置）后校验全绿、能发布——证明管道通，**不是**教研结论。

## 与 spec 的差异
1. **验收第 2 条“默认导入后没有孤点”没有做到**：14 个孤点的前置要么是自然语言（如“变量”“代数式”），要么在本专题外（如 `K-EQU-0901`），要么指向没导入的 P / C 节点。
   按默认规则（不猜映射、不连跨专题边）它们只能进工作单；结构类检查里 `cycle`、`transitive_edge`、`stale_cross_edge` 为零，`orphan` 要靠教研补前置才能清零。
2. 导入器放在 `tools/kge-inventory/src/import/` 而不是新建 `tools/kge-import`：复用同一套隔离加载器、图算法与依赖，不另起一个包。
3. 覆盖文件用 JSON 而不是 YAML：工具包没有 YAML 依赖，不为此引入新依赖（规则 10）。
4. 覆盖文件多了 `extra_prerequisites`（本专题内旧编码）：没有它，教研无法把自然语言前置落成边，孤点永远清不掉。补充前置造成环同样拒绝。

## 审查后的调整（按默认处理）
- **契约审查阻断 1**：库上测试拆成两段。第一段只用仓库里的种子（CI 没有 `legacy/`）；第二段（重新生成比对、合成补齐发布）没有 legacy 副本时打印“跳过”，严格模式也放行。
- **契约审查阻断 2**：未导入节点的每条前置都进工作单（“本节点未导入，这条边没连”），报告新增 `unconnected_edges`；二次函数 26 条。
- 主题段保留章节前缀（`FUN-CON` → `MATH.FUNC.FUN_CON`），一次函数、反比例函数并入同一领域时不撞 ID；同一主题 ID 对应两个簇直接报错。
- 库上测试按对象逐条比对：报告输出 `expected_orphans`、`expected_missing_boundary`，与 `validate_map_version` 的 `object_id` 排序后一致；
  断言种子以 `starbuddy_kge` 写入、固定 `standard_conforming_strings`；合成补齐保留 2 个易错点，覆盖错因大类的入库路径。
- 覆盖文件逐字段运行时校验：未知键、拼错的节点编码、类型不对、超过 32 条或 200 字、控制字符、疑似个人信息（手机号、身份证号、邮箱、“某某同学”）一律拒绝；
  类型与字段不匹配（方法带认知层次、非易错点给错因）报错。工作单写明“典型题例只写合成题或题目 ID，不得粘贴学生作答”（规则 13）。
- legacy 子进程输出按不可信数据核对（类型、长度、条数）；专题代码在 `build()` 里也校验；SQL 拒绝控制字符。
- 纵深防御：加载 legacy 前拿掉全局 `fetch` 等网络接口、封掉 `process.getBuiltinModule`；这不是禁网边界（见待人确认 #7）。
- 单测补齐：未连接边、预期清单、权重 1、边去重、主题撞名、不可信输入、反斜杠与角色。

## 经验
- **阿鸦的 P 类看起来是“性质”，不是“易错点”**：二次函数里 14 个 P 节点是“抛物线对称性”“开口方向”“增减性”“顶点式顶点坐标”这类核心性质，
  按默认 `P → pitfall` 且缺错因就不导入，等于把一半核心知识挡在地图外。试算：`P → kp` 后导入 38 个、前置边 24 条、孤点降到 10 个。强烈建议教研复核待人确认 #2。
- 生成物必须可复现：地图版本 ID 由“学科 + 版本号”确定性派生，输入顺序不影响输出；库上测试先比对重新生成的文件与仓库种子，种子过期即失败。
- 种子 SQL 以 `SET LOCAL ROLE starbuddy_kge` 写入，演练时用的就是知识服务的真实权限，不依赖超级用户。

## 待人确认
1. **P 类映射**（最要紧）：改为 `P → kp`（性质类知识点），还是逐个判断哪些是真正的易错点？一旦定下，在覆盖文件 `kind_map` 或逐节点 `kind` 里写明，重新生成即可。
2. 14 个孤点的前置映射：自然语言前置落到哪个节点、跨专题前置（`K-EQU-*` 等）是否随“方程”专题一起导入后再连边。
3. 20 个节点的包含 / 不包含 / 典型题例 / 认知层次：由教研按工作单填写（不从 `core` 自动推）。
4. 7 个能力子节点（C）是否登记为能力视图（`platform.skill_node` 已有），还是另建能力视图表；ADR 11 签字时一并定。
5. 种子 SQL 何时、在哪个演练库执行：依赖迁移 0011（草稿，由人执行）。
6. 未导入的 21 个旧编码没有进 `kge.id_migration`：设计文档规定“无法可靠迁移 → retire”，但 retire 会让对应掌握度变成“待复测”，不自动写；
   类型映射定下后重新生成即可登记，作为发布前的前置条件（契约审查建议 6）。
7. 加载 legacy 的子进程能联网（Node 权限模型不管网络，沿用 KGE-00 的做法）：是否要求在无网络环境（`unshare -n` 或无网容器）里运行导入器。
8. 一次运行只生成一个专题、地图版本 ID 只由“学科 + 版本号”派生：第二个专题用同一版本号会撞唯一约束，发布 0.1.0 则阿鸦的地图只有二次函数一章。
   KGE-02 扩到多个专题时改成一次构建多专题（契约审查建议 2）。
