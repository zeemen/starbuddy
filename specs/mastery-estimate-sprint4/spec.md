## 开发计划 v2.0 的影响（2026-09-27）

v2.0 冲刺 4-C 改为 **KGE-04 掌握 v0**：“规则 + 简化 BKT、五道门槛、星亮门槛由教研配置、0 / 3 / 14 天复测；学情档案页模板渲染 + 惰性编译 + 陈述—判断一致性检查（境内模型）”，验收“‘刷同题’无法点亮；一致性检查拦截程度升级”。掌握计算以 KGE V1.1 第六章为准，证据对掌握与置信度的影响方向以 SIE V1.1 第五章证据权重表为准。

与本 spec 的差异：
1. **计算单元**：从“学生 × skill_node”改为“学生 × knowledge_node × 认知层次”（KGE `mastery_estimate(student_id, node_id, level, …)`）。skill_node 只作能力视图，由节点证据按标签加权聚合，不单独点亮。前提是 KGE-01 骨架与 KGE-02 原子层（v2.0 冲刺 1、2），仓库里还没有（对照文档待决 #4、#8）。
2. **证据分类**：evidence_event 需要 `evidence_kind`（independent / hinted / transfer / delayed_retest）与 `map_version`，现表没有（待决 #5）。本 spec 的“哪些作答算数”要改写成按四类证据与提示等级加权：
   - 独立做对明显上调；低级提示（阶梯前 1/3）后做对小幅上调；
   - 高级提示或看过讲解后做对不变，只记“辅导有进展”，并自动安排无提示变式；
   - 变式或跨章独立做对计入迁移；间隔 ≥ 7 天的延迟复测做对明显上调；
   - 独立做错按错因下调、置信度上调；C 级识别作答不参与；学生自述“我会了”不改变，只触发验证题。
3. **五道门槛**：理解 → 执行 → 稳定 → 迁移（星亮）→ 保持，对应本 spec 的 state 判定；星亮默认门槛“不同题型多次独立正确、提示依赖低、间隔复测通过”，数值仍由教研配置（必停项：判分与掌握计算逻辑）。
4. **时间衰减**：长期无新证据时降低置信度、不清零掌握度，由复习调度安排复测；到期的相关判断转“待验证”由洞察服务处理，不在本模块。
5. **新增范围**：学情档案页（每生每科一页）模板渲染为主，模型只写排序与衔接语；每条陈述引用判断 ID；惰性编译（会话开始时过期才重编、周报时编一次）；陈述—判断一致性检查（程度升级或新增结论即阻断）；档案页只存个人层，不进入知识页面仓库，编译只用境内已备案模型。它依赖 SIE 判断账本（v2.0 冲刺 4-L SIE-02b），本 spec 原先完全没有这部分。
6. **写入分工**：Agent 与适配器只经 `evidence.write` 写证据；掌握由成长引擎计算；判断由洞察服务写（CLAUDE.md 规则 11）。
7. **RLS 与删除**：KGE-04 要求个人层全部表启用 RLS，并被家长删除请求覆盖（Gate 0“画像底线”：删除覆盖全表）。
8. **表放在哪个 schema**：待对照文档待决 #3；决定前沿用 `platform.mastery_estimate`，本 spec 的“迁移 0012”编号作废待重排。

## 目标
学习服务根据平台上已有的作答证据，为每个学生的每个能力点算出一条当前掌握记录，写入 `platform.mastery_estimate`，并排好下一次复测。

完成后：
- 星图（3-H）上的星第一次有了真实来源，不再只靠合成种子。
- 同一道题反复答对，星不会亮。要亮，必须“不同题、不同题型、低提示、隔几天再答对”，并且用的是已准入的题。
- 到了 0 / 3 / 14 天，平台上有一条可查询的复测任务。
- 对任何一颗星，都能回答“为什么亮了 / 为什么没亮”，答案落到具体条件和证据 ID。

## 设计要点

### 1. 谁算、什么时候算
- **只有学习服务算**，以 `starbuddy_learning` 身份写。新代码放在 `services/learning/learning/mastery/`。BFF、前端、适配器都不算（规则 2）。
- **三个触发点**，走同一个函数 `recompute(student, subject, skill)`：
  1. **落库之后，同一个请求里**：`grade` / `diagnose` 的落库事务提交后，另起一个事务，重算这次涉及的能力点。
     - 重算失败只记日志和指标，**不影响**已经落库的证据，也不改接口返回。
     - 这样星的变化基本是即时的，阿鸦“尾巴发光与星亮同一时刻”才有可能做到（4-H 负责）。
  2. **定时对账**（第 7 节）：补上漏算的能力点，维护复测任务。
  3. **按题重算**：`recompute_item(subject, item_id)`，给 4-G 在题目准入状态变化时调用（例如题被改为 `rejected`）。
- 幂等重放（`ingest_request` 已成功）直接返回，不触发重算。漏掉的由定时对账补。
- 没有门槛配置的学科（文砺、知行、开口成章）一律跳过，不写记录。

### 2. 哪些作答算数
重算时读取该学生该能力点的全部作答，逐条判定“计入”还是“不计入”。不计入的原因都有编码，解释时列出。

一次作答要**计入**，必须：
- 能对上一个判分：
  - `grade`：当前（未被取代）的 `grade_result`，按 `attempt_id` 对上；
  - `diagnose`：当前的 `skill_observation`，其 `evidence_ids` 包含这次作答的 `response_evidence_id`。
- 判分只来自验证器或 Rubric 的结果（规则 3）。答对 = `verdict = correct` 或 `outcome = demonstrated`；答错 = `incorrect` 或 `not_demonstrated`；其余（`partial`、`inconclusive`、`needs_review`、`not_applicable`）不计入。
- 判分置信度 ≥ 配置值（默认 0.8）。否则不计入，编码 `low_confidence`。
- 需要复核的判分：
  - 复核原因只有 `content_not_admitted` 的，可以计入，但最多推到 `stable`；
  - 有其他复核原因（边界题、主观维度、学生申诉等），结案前一律不计入，编码 `pending_review`（待人确认 #10）。
- 能力点按 `platform.item.skill_local_id` 归属，也就是题目的第一个主节点（待人确认 #21）。

另外几条“答对也不算答对”的规则：
- 自评“猜的”答对：不计入，编码 `guessed`。
- 提示等级高于配置值（默认 > 2）：答对只算“理解”层的证据，不算执行及以上，编码 `hint_heavy`。
- `hint_level_used` 缺失：按“不是低提示”处理（待人确认 #9）。

### 3. 每个 state 的判定条件（默认配置 `aya-t1`，数值待教研签字）
重算是**按时间重放**：把计入的作答按 `recorded_at` 排序，从 `unseen` 开始逐条推进状态。同样的证据、同样的配置，永远得到同样的结果。

下表中“新题”指该学生在这个能力点上**第一次作答**的题；“低提示”指提示等级 ≤ 2 且不是“猜的”。

| state | 条件（全部满足） | 星图 |
|---|---|---|
| `unseen` | 有计入的作答，但一道都没答对 | 未亮 |
| `understand` | 至少 1 道题答对，提示等级不限 | 未亮 |
| `execute` | 至少 2 道**不同的**新题低提示答对；BKT `p` ≥ 0.5 | 半亮 |
| `stable` | 已是 `execute`；**0 天复测通过**：到达 `execute` 至少 30 分钟后，又一道新题低提示答对；累计至少 3 道不同的题低提示答对，覆盖至少 2 个**题型组**；`p` ≥ 0.7 | 半亮 |
| `transfer`（星亮） | 已是 `stable`；**3 天复测通过**：到达 `stable` 满 72 小时后，第一道已准入的新题低提示答对；**只用已准入、`formal`、不需复核的作答**重新检查 `stable` 的全部条件，仍然满足；`p` ≥ 0.85；配置已由教研签字 | 亮 |
| `retain`（保持） | 已是 `transfer`；**14 天复测通过**：到达 `transfer` 满 14 天后，第一道已准入的新题低提示答对 | 亮 + 外圈 |

- 没有任何作答的能力点不写记录，星图按“无记录”显示为未亮。
- 题型组由配置把题型映射成组。阿鸦默认两组：选择（单选、多选）、填空（待人确认 #3）。
- **配置未签字时最多写到 `stable`**。这样教研签字前，不会出现真实的亮星。
- 点点规格书的“接近掌握”（过了执行、没过稳定或迁移）对应 `execute` 与 `stable`，不需要额外字段。

### 4. BKT 在里面的角色
- **规则决定能到哪一层，BKT 只做“下限”**。每一层除了规则条件，还要求 `p_mastery` 不低于该层的下限（上表）。
  - 作用：规则都满足、但最近连续答错时，BKT 会把 `p` 拉低，挡住晋级。
  - 规则负责“可解释”，BKT 负责“最近的表现”。
- 标准四参数 BKT，按学科配置：`p_init`、`p_learn`、`p_slip`、`p_guess`。`p_guess` 按题型给（默认单选 0.25、多选 0.1、填空 0.05），其余默认 `p_init` 0.2、`p_learn` 0.15、`p_slip` 0.1（待人确认 #16）。
- 输入序列与第 2 节一致：只用每道题的**第一次**计入作答，重做不进序列。
- v0 不做遗忘项。遗忘靠间隔复测处理（完整方案第四章“遗忘复习用间隔规则起步”）。
- 自己写，几十行 Python，不引入 pyBKT 等依赖（规则 10）。
- 参数没有校准，配置里标 `calibrated: false`，解释里如实显示。

### 5. “刷同题”防护
| 刷法 | 防护 |
|---|---|
| 同一道题反复答对 | 每道题只计**第一次**作答，之后重做只记录、不计入，编码 `repeat_item`（待人确认 #8）。执行及以上都按“不同的题”计数。 |
| 同一条证据重复提交 | 同 key 重放不写行（`ingest_request`）；同一 `evidence_id` 只登记一次（`evidence_registry`）；重算按 `attempt_id` 去重。 |
| 换个 key 重复提交同一作答 | 是同一道题，按上一条处理。 |
| 靠提示做对 | 提示等级 > 2 的答对只推到 `understand`。 |
| 猜对 | 自评“猜的”不计入。阿鸦 `diagnose` 已把这类观测的置信度压到 0.3，低于计入门槛。 |
| 同一题型刷 | `stable` 要求至少 2 个题型组。 |
| 连着做、当场“复测” | 0 天复测要隔 30 分钟以上，3 天、14 天复测按小时算足。 |
| 改客户端时间提前“过”间隔 | 间隔一律按服务器写入时间 `recorded_at` 算，不用客户端给的 `occurred_at`（待人确认 #7）。 |
| 复测失败了换题再试，直到做对 | 每一轮复测只看**到期后的第一道**符合条件的题，做错就算失败（第 8 节）。 |
| 用未准入的题点亮 | 见第 6 节。 |

题目换数字、换顺序的“近似题”，v0 识别不了。只能靠教研在内容包里标“同族题”，平台再按族计数，这不在本冲刺（写入 lessons 的待人确认）。

### 6. 只让已准入内容推动 `transfer` 及以上
- 准入状态取“证据落库时的 `admission`”与“题目**当前**登记的 `admission`”里更严的那个，与 `store.py` 第 116–130 行同一规则。
  - 结果：题目后来被撤销（`rejected`），依赖它的亮星会在重算时退回 `stable`；
  - 题目后来才准入，之前在未准入状态下的作答**仍算未准入**，不追溯点亮（待人确认 #11）。
- 判定 `transfer` 与 `retain` 时，只用“已准入、`semantics = formal`、不需复核”的作答，**重新**检查所有条件（不同题数、题型组、复测）。未准入作答只影响 BKT 与 `understand`–`stable`。
- 3 天、14 天复测只认已准入的题。未准入的题在复测期里做对做错，都不算复测。
- **写库前自检**：准备写 `transfer` / `retain` 时，逐条核对 `evidence_ids` 对应的题都已准入。不满足就拒绝写入，并报警。这是表注释那条不变量的落实。

### 7. 复测调度
**时间点**：
| 轮次 | 何时排 | 到期时间 |
|---|---|---|
| 0 天 | 到达 `execute` 时 | 到达时刻 + 30 分钟 |
| 3 天 | 到达 `stable` 时 | 到达时刻 + 72 小时 |
| 14 天 | 到达 `transfer` 时 | 到达时刻 + 14 天 |

- “到达时刻”是促成晋级的那次作答的 `recorded_at`，所以到期时间只取决于证据，重算多少次都一样。
- `mastery_estimate.next_retest_at` 写这个到期时间。它是复测时间的**真相源**。
- 到达 `retain` 之后，v0 不再排复测，`next_retest_at` 为空（待人确认 #14）。

**复测任务**（默认新表，待人确认 #4）：`platform.retest_task`
- 字段：`id`、`student_id`、`subject`、`skill_local_id`、`rung`（0 / 3 / 14）、`due_at`、`status`（`open / passed / failed / cancelled`）、`reason`（`scheduled / early`）、`scheduled_by_estimate_id`、`closed_at`、`closing_attempt_id`、`created_at`。
- 不存题目、答案、作答内容。
- 每个学生每个能力点最多一条 `open`（部分唯一索引）。
- **生成时机**：写入带 `next_retest_at` 的掌握记录时，在**同一个事务**里建任务。只要掌握记录写成功，任务就一定在。“到期”由 `due_at ≤ now()` 判断，不需要再改状态。
- **关闭**：重算发现这一轮复测通过或失败时，同一事务里把任务改为 `passed` / `failed`，记下是哪次作答；排程变了（例如题被撤销导致退级），旧任务改为 `cancelled`。
- **逾期不降级**：学生错过复测，任务一直开着，星不变（待人确认 #15）。
- 复测用哪道题，4-C 不管。选题由 `plan`（4-D）或统一壳（4-H）按 `generate_variation` 从已准入题库里选，并排除做过的题。

**定时对账任务**：`python -m learning.jobs mastery-sweep`
- 一次性执行入口，以 `starbuddy_learning` 身份运行，和 2-E 计量任务的做法一样；接入真正的调度器等 ADR 03 / 10。
- 每次运行做三件事：
  1. 找出最近 48 小时内有新作答、新判分或新观测的能力点，逐个重算。重算是幂等的，重复处理没有副作用。
  2. 核对每条带 `next_retest_at` 的当前记录，都恰好有一条对应的 `open` 任务；缺了补上，多了取消。
  3. 输出计数：重算数、写入数、补建任务数、到期未做的任务数。
- 小批量、每个能力点一个事务，持锁时间短。
- 时钟可注入（只在服务里，数据库的 `computed_at` 仍是真实时间）。测试用合成证据的 `recorded_at` 加上注入的“现在”推进时间。

**为什么不用 `starbuddy_scheduler`**：它没有表权限，要用它就得把整套判定写成 `SECURITY DEFINER` 的 SQL 函数，BKT 和解释都得用 SQL 写。默认不这样做（待人确认 #6）。

### 8. 复测失败与退级
| 当前 | 这一轮复测失败 | 结果 |
|---|---|---|
| `execute` | 0 天 | 保持 `execute`；30 分钟后再排一次 0 天复测 |
| `stable` | 3 天 | 保持 `stable`；从失败时刻起再排 3 天 |
| `transfer` / `retain` | 14 天（或提前复测） | 写一条新的 **`stable`** 记录（星退回半亮）；从失败时刻起排 3 天，重新走 3 天 → 14 天 |

- 已亮的星，普通练习做错**不直接熄灭**。如果 BKT `p` 跌到 `stable` 的下限以下，把复测提前到当下（新建一条到期时间为“现在”的 14 天轮任务，`reason = early`）。复测再失败才退回半亮（待人确认 #13）。
- 证据被撤销（判分被更正、题目被撤销准入）时，重放自然得到更低的状态，照常写新记录。

### 9. 写入、更正与历史
- 每次重算得到一个结果：`state`、`p_mastery`、`confidence`、`next_retest_at`、`algorithm_version`、`evidence_ids`。
- **只有结果有实质变化才写新记录**：`state`、`next_retest_at`、`algorithm_version` 任何一项变化，或者 `p_mastery`、`confidence` 变化 ≥ 0.05（待人确认 #17）。否则什么都不写。
- 写新记录的顺序（原因见“现状”）：生成新 ID → 旧记录置 `is_current = false`、`superseded_by = 新 ID` → 插入新记录。三步在一个事务里。
- 旧记录不删不改内容，就是历史。周报（5-H）的 `mastery_history`（契约第 1219 行）从这里取。
- **`algorithm_version`**：同时带算法版本和门槛配置版本，例如 `mastery-aya@0.1.0.t1`。符合 `versioned_name` 的格式。
- **`confidence`**：默认 = 计入作答的判分置信度均值 × n / (n + 2)，上限 0.95。只有 1–2 道题时低于 0.5，星图会标“待验证”，与 3-H 的阈值一致（待人确认 #20）。
- **`evidence_ids`**：所有计入作答的作答证据 ID（`response_evidence_id`）。没有计入作答就不写记录。

### 10. 幂等与并发
- 重算前先对 `(student, subject, skill)` 取事务级 advisory lock（`pg_advisory_xact_lock`，键由三者哈希得到）。同一能力点的重算因此串行：落库后的同步重算、对账任务、按题重算互不踩踏。
  - 用 advisory lock 而不是锁当前记录，是因为第一次写入时还没有记录可锁。
- 拿到锁后重新读当前记录再比较。结果没有实质变化就不写，所以同样的输入重算任意次，最多写一次。
- 兜底：万一还是撞了唯一索引或 `guard_supersede`（“已被取代”），整个事务回滚，重试一次；再失败留给对账任务。
- 不同能力点之间没有共享锁，互不阻塞。

### 11. 门槛配置的存放与版本
默认放在仓库里，不建表（待人确认 #2）：
- 路径：`services/learning/learning/mastery/config/<subject>.<版本>.json`，v0 只有 `aya.t1.json`。
- 内容：题型分组、提示等级上限、判分置信度下限、各层的不同题数与题型组数、复测间隔、BKT 参数与各层 `p` 下限、`confidence` 公式参数、`calibrated`、`approved_by` 与 `approved_at`（教研签字）。
- 启动时按 JSON Schema 校验，不合法就拒绝启动。
- **一经使用就不改**，改数值只能新增一个版本。当前生效的版本由服务配置指定。
- 签字记录写在本 spec 目录的 `lessons.md`，配置文件里的 `approved_by` 与之对应。未签字的版本最多写到 `stable`（第 3 节）。
- 换版本后，由对账任务逐步重算（或手动全量重算），`algorithm_version` 变化会写新记录，历史可追溯。

### 12. 可解释性
- `explain(student, subject, skill)`：用当前记录的配置版本重放，返回：
  - 当前 `state` 与下一层；
  - 下一层每个条件：编码、是否满足、当前值、要求值、相关证据 ID。例如 `distinct_items: 2 / 3`、`item_type_groups: 1 / 2`、`retest_d3: 未到期（到期时间）`、`admitted_only: 不满足（0 道已准入）`；
  - 每条不计入的作答及原因编码：`repeat_item`、`guessed`、`hint_heavy`、`low_confidence`、`pending_review`、`not_admitted`、`not_formal`、`retest_too_early`。
- **只输出编码与数字，不输出自然语言**。给学生、家长看的话术由人设层或周报生成，本冲刺不写话术（规则 7）。
- v0 只提供服务内函数和一个开发用命令行（只连开发库、只用合成数据），不开 HTTP 接口（待人确认 #19）。
- 能这样做的前提是：算法是确定性的，配置按版本保存不改。

### 13. 与其他模块的接口
- **星图（3-H）**：不用改。星图只读 `state` 与 `confidence`。复测失败写 `stable`，星自然退回半亮。
- **周报（5-H）**：从 `mastery_estimate` 的历史记录取 `mastery_history`；“本周点亮的星”= 本周新写的 `transfer` 记录。解释的对外接口到那时再定。
- **计划（4-D 阿鸦 `plan`）**：平台把当前 `state` 与 `next_retest_at` 放进 `PlanRequest.mastery`（契约第 758 行已有这两个字段），适配器可以产出 `kind: retest` 的任务（第 788 行起）。复测的真相源仍是平台的 `next_retest_at` 与 `retest_task`。
- **统一壳（4-H）**：读 `retest_task` 显示“待复测”；按掌握记录的变化触发点亮动效。作答时要带上 `hint_level_used`，否则只能到 `understand`。
- **发布闸门（4-G）**：题目准入状态变化时调用 `recompute_item`。

### 14. 测试
- **单测**（纯函数，不连库）：重放状态机、BKT、配置校验、解释。每条规则都有正例和反例。
- **集成测试**（一次性 Postgres，与 `learning-test` 同一套）：合成学生、合成题目，覆盖下面“验收标准”的全部场景。
- **全库不变量**：每个集成测试结束时跑一条 SQL，断言没有任何 `transfer` / `retain` 记录引用了未准入题目的证据；每个学生每个能力点至多一条当前记录；每条带 `next_retest_at` 的当前记录都有一条对应的 `open` 任务。
- **变异测试**：去掉“不同题”判定、去掉提示等级判定、去掉准入判定、把间隔改成按 `occurred_at` 算、去掉 advisory lock，每条都必须被测试发现。
- 全部数据是合成的（规则 8）。

## 验收标准（可测试）
- [ ] **“刷同题”无法点亮**（开发计划验收）。集成测试，合成学生，全部题目已准入、配置已签字，逐项断言最终状态：
  - 同一道题分 20 天、每天换 key 答对一次，提示 0 → 最高 `understand`；
  - 同一请求重放 20 次、20 个并发同 key → 行数不变，掌握记录只写一次；
  - 3 道不同的题都答对但同一题型 → 最高 `execute`；
  - 全部用 3 级提示答对 → 最高 `understand`；
  - 自评“猜的”答对 → 不计入，解释里有 `guessed`；
  - 3 天复测提前 1 小时作答 → 不算复测，解释里有 `retest_too_early`；
  - 把 `occurred_at` 提前 3 天、`recorded_at` 是现在 → 不算过了间隔；
  - 3 天复测失败后换题再做对 → 这一轮仍记失败，要从失败时刻重新等 3 天。
- [ ] **未准入不点亮**：条件全满足，但题目是 `source_unverified` / `pending_review` → 最高 `stable`。题目改为 `rejected` 后按题重算 → 亮星退回 `stable`，旧记录被取代。全库不变量 SQL 通过。
- [ ] **未签字不点亮**：配置 `approved_by` 为空时，条件全满足也最高 `stable`。
- [ ] **正常路径能点亮**：合成学生按“2 题 → 30 分钟后新题 → 72 小时后新题 → 14 天后新题”作答，状态依次为 `execute`、`stable`、`transfer`、`retain`，每一步都有新记录，旧记录 `is_current = false` 且指向新记录。
- [ ] **复测任务按时生成**（开发计划验收）。注入时钟：
  - 到达 `execute` / `stable` / `transfer` 时，同一事务里出现 0 / 3 / 14 天任务，`due_at` 分别精确等于到达时刻 + 30 分钟 / 72 小时 / 14 天，且等于 `next_retest_at`；
  - `due_at` 之前查“到期任务”查不到，之后查得到；
  - 手动删掉一条任务后运行对账 → 补回且只有一条；对账连跑三次，任务数不变；
  - 复测通过或失败后，任务状态分别为 `passed` / `failed`，并记下作答 ID。
- [ ] **复测失败退回半亮**：`transfer` 后 14 天复测答错 → 新记录 `state = stable`；BFF 的 `toDisplay` 对它返回 `half`。
- [ ] **幂等与并发**：同一能力点 20 个并发重算 → 只有一条当前记录，更正链完整，没有错误抛到调用方；同样的输入重算两次，第二次不写行。
- [ ] **重算失败不影响落库**：注入重算异常 → `grade` 仍返回 200，证据完整落库；之后运行对账，掌握记录补上。
- [ ] **规则 6**：每条新记录的 `algorithm_version` 含配置版本；`confidence` 非空；`evidence_ids` 非空，全部存在，并且都属于同一学生、同一学科、同一能力点。
- [ ] **可解释**：上面每个场景都调用 `explain`，断言未满足的条件编码与不计入原因编码符合预期；解释里的证据 ID 都在记录的 `evidence_ids` 或不计入清单里。
- [ ] **没有配置的学科不写**：文砺的合成证据不产生任何掌握记录。
- [ ] **`retest_task` 的 RLS**（规则 5）：学生本人、已绑定家长能读；兄妹、另一户家长、撤销绑定后都读不到；BFF 不能写；复核与调度角色没有权限。
- [ ] 变异测试全部被发现。
- [ ] 严格模式 `make check` 通过。

## 待人确认
1. **各层判定条件与默认数值**（第 3 节表格）。默认按 `aya-t1` 草案实现，教研签字前最多写到 `stable`。另一个选择：先等教研给出数值再开工。
2. **门槛配置放在哪里**。默认是仓库里的版本化 JSON 文件，改数值走 PR，签字记录在 lessons。另一个选择：平台建配置表，教研可以不经发版修改；这要迁移（必停），还要一个教研身份的写入入口。learner-schema spec 第 25 行原先设想的是“配置表”。
3. **题型从哪里来**。默认在 `platform.item` 加 `item_type` 列，由登记脚本写入；阿鸦分“选择”（单选、多选）与“填空”两组。另一个选择：契约让适配器在证据里带题型（契约变更，必停）。单选与多选算不算不同题型，由教研定。
4. **复测任务存在哪里**。默认新表 `platform.retest_task`（迁移 + RLS）。另一个选择：不建表，“待复测”直接从 `mastery_estimate.next_retest_at` 查；这样不用迁移，但复测的通过、失败没有独立记录，也不好统计完成率。
5. **什么时候算**。默认落库后在同一请求里另起事务同步算，加定时对账兜底。另一个选择：全部交给异步任务，接口更快，但星的变化会延迟到下一次任务运行。
6. **定时任务用什么身份跑**。默认学习服务的一次性入口，以 `starbuddy_learning` 身份运行。另一个选择：用 `starbuddy_scheduler` 调 `SECURITY DEFINER` 函数，与 2-E 一致，但判定逻辑要写成 SQL。
7. **间隔按哪个时间算**。默认服务器写入时间 `recorded_at`。另一个选择：客户端的 `occurred_at`，补录纸质作业时更准，但可以被伪造。
8. **同一道题重做算不算**。默认每道题只计第一次作答。另一个选择：隔 N 天以上重做可以再计一次（N 由教研配置）。阿鸦 247 个能力点只有 1 道题，这个选择会明显影响能点亮的星数。
9. **没有提示等级怎么办**。默认按“不是低提示”处理，最多到 `understand`。另一个选择：不提供提示的场景（如入口诊断）按 0 处理，由请求模式决定。
10. **需要复核的判分**。默认只有 `content_not_admitted` 一个原因的可以计入到 `stable`，其他原因结案前不计入。另一个选择：凡是需要复核的一律不计入；那样在阿鸦内容准入之前，连半亮都没有。
11. **准入以哪个时间点为准**。默认取证据落库时与题目当前登记里更严的那个，后来准入的题不追溯。另一个选择：以题目当前状态为准，4-G 发布后，学生以前做过的题可以追溯点亮。
12. **0 天复测的间隔**。默认至少 30 分钟。另一个选择：同一天任意时间，或“下一次学习会话”。
13. **已亮的星做错普通练习**。默认不直接熄灭，`p` 跌破 `stable` 下限时把复测提前到当下。另一个选择：`p` 跌破下限就直接退回 `stable`。
14. **到达“保持”之后**。默认 v0 不再排复测。另一个选择：每 30 天一次维持性复测。
15. **错过复测**。默认不降级，任务一直开着。另一个选择：逾期超过 N 天退回 `stable`。
16. **BKT 参数**。默认 `p_init` 0.2、`p_learn` 0.15、`p_slip` 0.1，`p_guess` 按题型（单选 0.25、多选 0.1、填空 0.05），标“未校准”。另一个选择：沿用阿鸦 legacy 的固定参数（要先到 legacy 代码里核实数值）。
17. **什么时候写新记录**。默认只在状态、复测时间、算法版本变化，或 `p`、`confidence` 变化 ≥ 0.05 时写。另一个选择：每次重算都写，周报趋势更细，但表增长快。
18. **复测作答扣不扣额度**。现在 `grade` 都按错题分析等资源计量（`0009` 第 72–82 行）。默认 4-C 不动计量，建议 4-H 让平台发起的复测不扣额度（届时是必停项）。另一个选择：复测照常扣。
19. **解释要不要对外开接口**。默认 v0 只有服务内函数和开发命令行。另一个选择：本冲刺就在 `learning-internal` 契约加一个查询接口给 BFF（契约变更，必停）。
20. **`confidence` 的算法**。默认“判分置信度均值 × n / (n + 2)，上限 0.95”，1–2 道题时星图显示“待验证”。另一个选择：由教研给公式，或直接取 BKT 后验的某个区间宽度。
21. **一道题有多个主节点**。阿鸦 83 道题是这样。默认只计入平台登记的第一个主节点。另一个选择：用 `diagnose` 的观测覆盖其余节点，但 `grade` 不产出观测，两条路径会不一致。
22. **复测间隔以哪个为准**。阿鸦 legacy 是 2 / 7 / 14 / 21 天，平台是 0 / 3 / 14 天。默认以平台为准，间隔放在配置里，教研可以按科改。另一个选择：阿鸦沿用 legacy 的间隔。
23. **开发库里的 3-H 合成种子**。对账任务会重算有新证据的能力点，可能把种子里手写的 `transfer` / `retain` 改掉。默认对账只处理最近 48 小时有新证据的能力点，种子被改掉就重跑种子。另一个选择：给对账任务加开关，跳过合成种子学生。
