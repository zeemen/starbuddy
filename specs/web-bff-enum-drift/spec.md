# 前端白名单与取值出处的一致性核对（防“取值静默漂移”）· 规格草稿

- 状态：**已确认（2026-11-12，用户“按建议，默认值都同意，开始实现”）**：第五节待人确认 1–3 全部按默认。实现记录见 lessons.md。
- 依据：`specs/review-console-responses/lessons.md` 补记（审核台响应模型的来源种类漏了 0036 的 `weekly_report`，严格校验下整页 500；
  教训是运行时严格的枚举都要有“对出处”的测试兜底）。CLAUDE.md 规则 11（判断先于展示：前端只显示经白名单收窄的取值）。
- 不涉及必停项：只加测试；不改契约、迁移、BFF 与前端的业务逻辑。若核对暴露真实的漂移，修法另记（可能牵涉契约或迁移，届时按必停处理）。

## 一、现状
- 前端信任界面、再练、复测各页把 BFF 的返回先当 `unknown`，再经 `pick*`（`apps/web/src/trust/view.ts`、`practice/view.ts`、`retest/view.ts`）
  逐字段收窄；收窄用十几组白名单：置信度分档、证据来源、异议类型与状态、下一步、考试科目与类型、偏差方向、调整、客观栏学科、周报段落、
  导出 / 删除范围、撤回原因、再练条目状态与来源、认知层次、判分结论等。
- 取值的出处各不相同：库里的 CHECK 或枚举类型（异议状态、周报段落、撤回原因、判分结论……）、契约 OpenAPI 的 enum（置信度分档、下一步、偏差方向……）、
  BFF 自己的常量（`services/bff/src/trust/clients.ts` 等，本身多是契约的转写）。
- 后果：出处多了一个取值，`pick*` 不报错，只把整块内容静默降级成“暂时无法获取”或丢掉那一条——用户看到空白，测试也不红。
  现有的逐字对照只有零散几处（内测反馈分类、富题面、星图正式显示规则）。2026-11-11 抽查 6 组，眼下都一致（BFF 多一个 `profile` 开关，有意为之、两边有注释）。

## 二、默认做法
1. **登记表**：新文件 `services/bff/tests/enum-drift.integration.test.ts`，一张表逐行登记“前端白名单 ↔ 出处”：
   出处三种——库（schema.表.列：读 CHECK 约束或枚举类型，同审核台 `test_review_responses_enums.py` 的做法）、契约（文件 + 字段路径：按缩进取 enum，
   不引入 YAML 依赖，同 `openapi-ops.ts`）、BFF 常量（直接 import）。前端白名单直接 import `apps/web/src/...`（只读，不改前端）。
2. **口径**：默认要求相同；有意更窄的（例如考试科目不显示英语）在表里写明“子集”与原因，比较时按子集；有意更宽的不允许（前端认得出处没有的值，说明前端过期）。
3. **范围**：上面第一节列的、在 `pick*` 里收窄 BFF 返回值的白名单（约 15 组）；BFF 常量本身是否与契约一致一并核对（BFF 常量登记它的契约出处）。
   壳、建档、星图等其余页面的白名单，有需要时照同一张表加行。
4. **变异**（接进 `services/bff/tests/mutations.sh`）：前端白名单少一个取值、多一个取值、出处多一个取值（库约束改写由测试里的临时表模拟，或改契约副本），各一条。

## 三、不做
- 前端遇到认不出的取值时的降级方式（现在是整块“暂时无法获取”或丢条）：要不要改成“认不出的那一条另行提示”属于产品与 SIE 口径，另起。
- 改契约、迁移或 BFF 的取值本身（核对发现漂移时另记、按必停处理）。

## 四、验收
- 登记表覆盖第一节列的白名单，全部一致（或按登记的子集）；新增变异全部被发现；`make bff-test`、`make bff-mutation`、`make web-test`（单测部分）通过。
