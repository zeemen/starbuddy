## 目标
1. 建立**一套与学科无关的契约一致性测试**（conformance suite）：对任何一个正在运行的适配器，只要给出地址、令牌和该科的合成夹具，就能跑同一套测试。测试从契约生成，期望来自消费方，也就是学习服务。
2. 把 `make check`（含这套测试）接入 CI，并以严格模式运行：缺依赖就失败，不能“跳过”变绿。
3. 按评审结论产出契约 **v1.0**，并在 W4 冻结。冻结本身要人签字。

完成后，冲刺 2–3 接入知行、文砺、开口成章时，每科只需要提供自己的合成夹具，不用再写结构性的契约测试；Gate 0 的契约覆盖率由这套测试直接统计。

## 现状（为什么要做）
| 已有 | 缺口 |
|---|---|
| `check_contract.py`：检查契约文档本身，包括 OpenAPI 合法性、17 个示例、55 个反例和 46 个变异 | 只检查文档，不检查任何一个运行中的适配器 |
| 阿鸦 `tests/contract.test.ts`：用 ajv 按契约校验自己的响应，覆盖全部 721 道题 | 是阿鸦自己写的测试，其他三科不能复用；而且和适配器出自同一个会话，违反执行方案第六章 |
| 学习服务 `learning/checks.py`：平台侧核对（证据闭合、学科一致、准入与效力、作答证据等） | 这些正是消费方的真实期望，但只在学习服务里运行，适配器开发时发现不了 |
| 仓库没有 CI（`.github/` 不存在） | `CONTRACT_STRICT=1` 还没有地方可设；分支保护也未核验 |

## 范围

### 做
1. **共享的平台侧核对库** `packages/contracts/python/starbuddy_contract/`：
   - 把学习服务里与数据库无关的核对规则（`checks.verify` 中的纯函数部分）连同契约加载器一起移到这里。
   - 学习服务改为引用这个库，行为不变，学习服务现有的 47 个测试照常通过。
   - 这样“消费方的期望”只有一份，学习服务和一致性测试用的是同一段代码。这就是本 spec 所说的“消费者驱动”：由消费方定义期望，提供方逐条满足（见待人确认 #1）。
2. **一致性测试运行器** `packages/contracts/conformance/`：Python + pytest，通过 HTTP 调用适配器，不依赖适配器的实现语言。
   - **输入**：适配器地址、服务间令牌，以及学科夹具文件 `adapters/<学科>/conformance/fixtures.yaml`（格式见下）。
   - **从契约生成的通用用例**，每个学科都跑：
     | 类别 | 内容 |
     |---|---|
     | 能力声明 | `GET /capabilities` 符合 schema，`subject` 与夹具一致，`contract_version` 等于契约版本 |
     | 未实现的方法 | 声明未实现的方法返回 501 `METHOD_NOT_IMPLEMENTED`，并且是合法的 Problem |
     | 请求校验（反例） | 对每个已实现的方法，由契约自动变出一组坏请求：缺 `idempotency_key`、消耗类缺 `usage_id`、`contract_version` 不对、`subject` 不对、`data_class` 为 L0/L1、多出字段等。都必须得到 4xx Problem，且 Problem 里不能回显学生原文 |
     | 响应合约 | 夹具里的每个合成请求，响应都要通过契约 schema，并通过共享核对库（证据闭合、学科一致、作答证据等于学生作答、`rubric_version` 一致、申诉进复核、未准入则为 practice……） |
     | 幂等 | 同一个 key、同一请求体重试，返回同一批 evidence_id；换了 `request_id` 也一样；同一个 key 换了请求体，返回 409 `IDEMPOTENCY_CONFLICT` |
     | 不泄露 | 响应里除学生原文以外，只能出现受控字符串（ID、编码、版本、时间），沿用阿鸦 `leak.test.ts` 的结构白名单做法；夹具里标注的“秘密”（例如标准答案）不得出现在任何响应里 |
     | 异步（如声明） | 202 受理回传 `usage_id` 与 `idempotency_key`，同一个 key 返回同一个 `job_id`，轮询结果与 method 绑定 |
   - **覆盖率报告**：按 capabilities 与实际通过的用例统计“六方法中几个已实现并通过”，输出机器可读的 JSON，供 Gate 0 使用（`/gate-check`）。
3. **学科夹具格式**：由各科维护，只放合成数据（规则 8）。每条夹具包括：
   - 方法；
   - 合成请求（可以省略 `context`，由运行器补全）；
   - 期望的结果类别：`verdict`、复核原因等**编码**，不写期望的完整结构；
   - 秘密字段清单，用于不泄露检查；
   - 需要预先登记的题目与能力点（运行器据此判断 `item_ref` 是否合法）。
   本冲刺先为阿鸦写夹具，从现有内容包挑样本：每种题型的正例、陷阱命中的反例、六类边界情况各一条。
4. **证明“四科共用”**：
   - 除阿鸦外，另写一个**参考假适配器**（`packages/contracts/conformance/reference_adapter.py`）。它按契约示例返回结果，可以扮演任何学科。一致性测试对它和对阿鸦跑的是同一套代码。
   - 再对参考假适配器做**变异测试**：逐一注入 10 类以上的违约行为，断言一致性测试都能发现。违约行为包括多出字段、证据 ID 不闭合、作答证据被改写、泄露秘密、幂等失效、未实现的方法返回 200 等。这和仓库里 `contract-mutation`、`db-mutation` 的做法一致，用来证明测试不是恰好通过。
5. **Makefile 与 CI**：
   - 新增 `make conformance SUBJECT=aya`：启动阿鸦适配器进程，跑一致性测试，结束后停掉进程。它也接入 `make check`。
   - 新增 `make conformance-mutation`，并接入 `make check`。
   - 新增 GitHub Actions 工作流 `.github/workflows/check.yml`：在 PR 与主干推送时运行 `make check CONTRACT_STRICT=1`。环境是 Ubuntu 加 PostgreSQL 16（apt 安装）、Node 22、Python 3.11，依赖都锁版本。
   - 契约检查同时覆盖 `learning-internal.v0.yaml`：OpenAPI 合法性，以及跨文件引用能解析（学习服务 lessons 的遗留项）。
6. **契约 v1.0 冻结**（分两步，第二步要人签字）：
   - **本冲刺**：把所有待定的契约问题汇总成一份评审清单 `specs/contract-conformance-sprint1/v1.0-review.md`。清单包含 v0.9 spec 的“待人确认”10 项、“留给评审决定”11 项，以及实现中新发现的问题。每项写明选项、默认建议和影响到的适配器。实现中新发现的问题包括：
     - 鉴权失败没有 Problem 编码（`UNAUTHENTICATED`）；
     - `needs_review` 暂不给分的表示方式；
     - 证据引用作答的 `attempt_id`；
     - `rule_ref` 注册表的语义；
     - 计分规则；
     - 按学科的 `item_ref` 前缀 if/then；
     - 可重试错误的“结果未知”语义。
   - **评审会（W4，人）拍板后**：按结论产出 `plugin-api.v1.0.yaml` 和变更记录，同步更新反例、变异、一致性测试、阿鸦适配器与学习服务，另开 PR。这个 PR 首行写 `[NEEDS-HUMAN]`。

### 不做
- 引入 Pact 等外部契约测试平台和 Pact Broker（见待人确认 #1）。
- 知行、文砺、开口成章的适配器与夹具（冲刺 2–3）。本冲刺只保证测试与学科无关，并用参考假适配器证明。
- 性能与负载测试（冲刺 5）。
- 在本冲刺内直接改契约。v1.0 的修改要等评审结论，单独开 PR。
- 开启 GitHub 分支保护：这是仓库设置，由人操作。本 spec 只给出建议配置。

## 待人确认
1. **“消费者驱动”的做法**：
   - 默认：不引入 Pact。把学习服务的平台侧核对抽成共享库，由它充当“消费方期望”，一致性测试直接调用它。好处是期望只有一份，和生产路径完全一致，也不用再搭一套服务。
   - 另一个选项：引入 Pact（pact-python，MIT 许可）加 Pact Broker。它适合多团队、多仓库，但本仓库是单仓，而且 Broker 是额外的服务。
   - 是否同意默认做法？
2. **夹具由谁写**：执行方案要求契约测试不由写适配器的同一个会话手写。
   - 默认：通用用例全部从契约生成；学科夹具只写“输入加期望编码”。
   - 夹具由另一个会话或该科负责人编写，并由教研抽查“期望 verdict”。
   - 阿鸦的夹具由谁写？
3. **CI 跑多少**：`make check` 全量约 4 分钟，其中数据库变异约 40 秒。
   - 默认每个 PR 都跑全量。
   - 如果要缩短，可以把 `db-mutation` 和 `contract-mutation` 只放到主干推送时跑。
4. **CI 平台**：默认用 GitHub Actions。仓库是私有的，Actions 分钟数是否有额度限制？另外，阶段 1 的境内托管（ADR 10）会不会要求 CI 也迁到境内？
5. **分支保护建议**：主干要求 PR、要求 CI 通过、要求至少一人审查、禁止强推。需要仓库管理员在 GitHub 设置里开启。
6. **v1.0 评审会的时间与参会人**：开发计划写的是 W4 冻结。评审清单预计在本冲刺第一周产出。
