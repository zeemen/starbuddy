## 交付
- `services/knowledge/knowledge/service/cache.py`：进程内 LRU（条目数缺省 1024、上限 10000；按条目 JSON 字节的总上限缺省 64 MiB；单条超过总上限 1/64 不入缓存），不设 TTL；入缓存与命中都深拷贝。
- 只缓存 `node.get`、`node.path`、`page.get`；键 = 工具 + 学科 + `map_version_id` + （page.get）快照 commit 与快照代号 + 按契约默认值补齐后的规范化参数（edition、region 入键，context 不入键）。每请求先查 `published_version`；只缓存成功结果；未知字段、学生 ID 类字段名（告警只记类别）、快照未配 / 页面不在快照 / 学科不明一律绕过；途中换了快照、无教材投影、单条过大的结果不入缓存。
- 热切换：`install` 递增快照代号并清空 page.get 条目；入缓存前再核对快照未换。缓存开着时只能经 `install` 换快照。
- 观测：访问日志 `cache` 字段（hit / miss / bypass，缓存关时不出现）；每 1000 次请求一条计数日志（按工具的命中、未命中、淘汰、绕过、未入缓存、条目数、字节数，只有数字）。
- 并发：知识服务单进程单事件循环，缓存方法全同步无 await，天然互斥，不加锁；改多线程或多 worker 时须加锁或换共享存储。
- 测试：知识服务 491 个（缓存 25 + 库上逐字节对比 1）；`knowledge-cache-mutation` 41 条全部发现（新目标，接进 check）；原 `knowledge-mutation` 164 条全部发现。

## 审查意见的处理（按默认）
- 契约阻断（安全审查以探针复现同一问题）：同一 commit 可按对账结果导出不同内容的快照，热切换恰在请求中途时旧页面会以新键入缓存并被长期命中 → 快照代号入键 + 入缓存前核对快照未换，两层都做；先在旧实现上复现失败再修。
- 采纳：告警不记原始键名；`node.path` 默认值补齐；字节上限与单条上限；无投影结果不入缓存；绕过计数与日志对齐；数值配置严格解析；定期计数日志；README 日志段。
- 偏差：计数日志只按次数不按时间；单条上限为比例而非独立配置；新增 `not_stored` 计数。

## 教训
- “换提交即换目录”不等于“同一提交内容唯一”：快照内容还取决于对账扣页等导出参数。用作缓存键的版本标识必须唯一标识内容，否则用安装代号。
- 跨 await 的缓存写入要核对写入时的版本仍是读取时的版本。
- 契约 `additionalProperties: false` 已拦住学生字段，缓存层的拦截只是第二道防线，只在契约校验被改坏时才生效。
- 本环境 `make contract-test` 缺依赖会跳过，审查结论里的“契约检查”须以严格 `make check` 为准。
