## 现状（调研结论）
- 用例、评分器、离线流程都有：`run.py --runs N` 能把 120 条用例经模型路由 test 环境（假供应商）跑 N 次并评分；报告不含回复原文，回复只能写到仓库外。
- **没有点点的人设层 Prompt**：仓库里没有点点的 System Prompt，只有规格书。没有 Prompt 就没法在真实模型上跑出有意义的首轮。
- **没有可用的候选模型**：试点、生产环境只能用已登记、境内的供应商，登记表为空；ADR 04 / 08 的候选名单没签字；本环境没有任何供应商凭据（规则 9，也不能自己新增供应商）。
- 评分器只出单次运行的通过率；没有“多家 × 多次”的汇总、差值与稳定性分析。

## 设计要点
### 1. 对照运行器（本任务完整实现，只用假供应商验证）
- `evals/persona/diandian/compare.py`：读一份候选清单（YAML：候选 ID、路由里的供应商与模型、说明），对每个候选把同一套用例、同一版人设 Prompt 各跑 N 次（默认 3），
  经模型路由调用（任务类型按人设对话，数据级别 L0：用例是合成输入）；每次运行单独评分。
- 候选只能来自模型路由配置里已登记的供应商；运行器不持有任何 Key，凭据只在运行环境（由执行人配置）。
- 回复原文只写到仓库外的执行人目录，用完删除；入库的只有不含原文的报告（沿用 1-I 的做法）。
- **留出集**：运行器默认不跑留出集用例；留出集由教研负责人在封存环境单独跑（规则 14），只出汇总。

### 2. 首轮差异报告（本任务完整实现）
- 每个候选：总通过率与按九类的通过率、红线命中数（任何红线命中单独列出）、3 次之间的稳定性（同一用例 3 次结果不一致的比例）。
- 候选之间：两两通过率差与 95% 置信区间（按用例配对的自助法，固定种子）；按类的差值热力表；“只在某一家失败”的用例清单（只列用例 ID 与检查点，不带回复）。
- 对照 3-I 的验收口径（三家在核心用例上通过率差 ≤ 5 个百分点），首轮只报告、不下结论；结论由人定（Gate 0：“人定”）。
- Markdown 与 JSON 两份；确定性输出（同样的输入逐字节相同）。

### 3. 用假供应商证明流程（本任务的通过条件）
- 测试里配置三家假候选：一家总是合规、一家在某类上稳定失败、一家随机失败；断言报告的通过率、差值、稳定性、区间与手算一致，红线单独列出。
- `make eval-persona` 增加对照运行器与报告的单测，不联网、不需要密钥。

### 4. 真实首轮（本任务不执行，交接给人）
- 前置清单写进 README：ADR 04 / 08 候选名单签字；供应商登记进 `vendors.md`（境内已备案）并加进模型路由配置；点点人设层 Prompt v0 经人设负责人审定；
  执行人在有凭据的环境里跑 `compare.py`，把不含原文的报告提交进 `evals/persona/reports/`。
- 在此之前，本任务交付的报告是用假供应商跑出的“流程样例”，明确标注“不是模型评测结果”。

## 验收标准（可测试）
- [ ] 对照运行器对三家假候选各跑 3 次，报告的通过率、差值、置信区间、稳定性与手算一致；红线命中单独列出。
- [ ] 报告与日志不含回复原文；回复只能写到仓库外；默认不跑留出集。
- [ ] 运行器只能调用模型路由里已登记的候选，不持有凭据；`make eval-persona` 通过；严格 `make check`、安全审查通过。
- [ ] 真实首轮的执行手册与前置清单写清楚；真实报告的产出不在本任务的通过条件里（记为后续验收）。
