# 冲刺 1-E：实现记录与待人确认

按 spec“待人确认”的默认方案实现（用户 2026-09-26 指示）：
1. 订阅挂家庭，额度桶按学生席位；
2. 周期滚动 30 天；
3. MAX 公平使用上限到顶硬停（`fair_use_margin` 默认 0）；
4. 预留过期时间、单次上限先填草案值；
5. 幂等键与学习服务共用一个；
6. 选科上限函数放到 2-E；
7. 试点虚拟额度按 PRO 发放，全量走账本（`source = 'pilot_virtual'`）；
8. 流水保留期待合规意见，本迁移不做清理。

## 结果
- **迁移** `0008_platform__metering`：8 张表、3 个视图、5 个触发器函数、种子。up → down → up 通过。
- **数据库测试** `db/tests/60_metering.sql`：102 项新断言，db-test 共 264 项。覆盖：
  - 种子与第八章逐格比对：28 格额度、16 格权益；
  - 配置生命周期：草稿 → 发布 → 停用；
  - 订阅归属；
  - 额度桶约束；
  - 预留状态机，用超级用户模拟 2-E 的函数：结算、复看、释放、过期；
  - 流水只追加与各项检查约束；
  - 分区；
  - 对账视图能发现四类篡改；
  - RLS：两户家长、学生本人、同手机号、未登录、学习服务、复核、授权属主。
- **变异测试**：新增 26 个，db-mutation 共 93 个，全部被发现。
- **设计文档** `docs/design/metering-schema.md`：ER 图、状态机、12 条不变式（每条对应测试与变异）、Gate 0 六类场景走读、与学习服务“结果未知”的时序、签字栏。

## 待人确认
1. **种子里付费档的 `diagnosis_screen` 是 0**：第八章只给普通会员写了“1 次筛查 + 1 次完整”，PLUS 及以上只写了完整诊断次数。现在按“付费档不单独给筛查”填 0。另一种读法是付费档的筛查不限次，或包含在完整诊断里。请产品负责人确认。
2. **预留过期时间与单次上限都是草案值**（spec #4）：

   | 资源 | 过期时间 | 单次上限 |
   |---|---|---|
   | 筛查、完整诊断、错题解析 | 10 分钟 | — |
   | 模考 | 150 分钟 | — |
   | 讲评课 | 90 分钟 | — |
   | 语音、AI 时长 | 30 分钟 | 30 分钟 |
   | 错题解析 | — | 20 题 |
   | 其他 | — | 1 |

   模考、讲评课的过期时间取的是“时长加余量”，不是 p99 的 2 倍，因为这两类是长会话。
3. **24 小时复看的去重范围是“家庭”**（按 spec 与 ADR 06 第 3 条）：兄弟姐妹在 24 小时内看同一道题，第二个人也不扣。但额度桶是按学生分的，所以第二个人的记录会指向另一个学生的首次扣费。如果希望按学生去重，只需把 `dedup_key` 的算法改成 `(学生, 资源类型, 内容指纹)`，表结构不变。请产品负责人决定。
4. **过期后迟到的成功不扣费**（设计文档场景 5）：宁可少扣不多扣。BFF 记指标，由人工决定是否补记。是否接受？
5. **`dedup_of` 的校验只在 2-E 函数里做**：包括指向的记录是否已结算、是否同一资源类型、是否在窗口内。数据库只保证“带去重键”和“指向真实预留”。原因是这些条件依赖时间与状态，放在 CHECK 或外键里做不到，放在触发器里又会和终态保护互相牵连。
6. **对账视图只给运维**：BFF 没有权限，也还没有专门的运维只读角色。巡检任务用哪个角色跑，需要和 ADR 03 调度一起定。
7. **`resource_type`、`plan_config` 的写入没有函数**：只能由迁移或人工（超级用户）写。发布新配置是否要走审批函数，以及由谁执行，待定。
8. **流水分区只建到 2027-12**（与证据表相同）：续建依赖 ADR 05 的调度任务，目前还不存在。超出范围的写入会直接失败，这是有意为之，便于告警。
9. **流水的 `actor` 多了一个 `system`**：spec 只写了“BFF 或人工”，但过期任务和周期授予既不是 BFF 请求，也不是人工操作，所以单独列出。

## 实现中的发现
- **流水外键需要 `entitlement (id, student_id)` 唯一**：第一版只有 `(id, student_id, resource_type)`，迁移执行失败。已补上。
- **测试一开始是“空转”的**：测试配置 `synthetic-plan@1` 只复制了额度、没复制权益，所以“已发布配置的权益不能改”那条 UPDATE 影响 0 行，断言本应失败却静默通过。测试报错后发现并补上。以后凡是断言“这条语句会被拒绝”，都要先确认语句确实命中了行。
- **余额视图必须是 `security_invoker`**：否则视图以属主（超级用户）身份执行，会绕过 RLS。已加变异“余额视图以属主身份绕过 RLS”证明测试守着这一条。
- **分区继承触发器**：`reject_ledger_change` 建在父表上，Postgres 会自动克隆到每个分区。直接 UPDATE 分区同样被拒，已有测试覆盖。
